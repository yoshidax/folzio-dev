# Feature Specification: 開発用リポジトリの公開の準備

**Feature Branch**: `claude/modest-euler-2bxq9s`（Cloud の作業ブランチ。feature 用のブランチは作らない）

**Created**: 2026-11-06

**Status**: Draft

**Input**: [TAK-80](https://linear.app/takyoshida/issue/TAK-80) 開発用リポジトリ folzio-dev を公開するための準備を整える

## 前提となる決定（2026-11-06、保守者）

- 保守者が、この feature の PR より先に、開発用リポジトリ（`yoshidax/folzio-dev`）を公開する。
  - 公開前の点検（秘密情報・個人の情報・非公開のつもりだった運用情報）は TAK-80 の Issue で済んでおり、公開から外すものはない。
  - コミット作者のメールアドレスは公開してよく、履歴は書き換えない。
- 2 リポジトリ方針は維持する。
  - 開発用リポジトリは、保守者が Spec Kit で開発を続け、開発の方法を共有する場とする。
  - 公開用リポジトリ（`yoshidax/folzio`）は、Spec Kit に縛られないプレーンな OSS の配布先とし、今の書き出しを維持する。
- 文書・README・書き出し・CI のトリガー・規則の変更は、この 1 つの PR にまとめる。
- Agent が CI を起動・再実行する前に保守者の許可を求める規則（TAK-53）は、なくす。
- 「PR は保守者の依頼があったときだけ作る」規則は残し、費用に関する理由の記述だけを消す。
- `master` のブランチ保護は、必須チェックだけにする（承認レビューは必須にしない）。設定は保守者が GitHub で行う。
- `master` への統合は、ローカルの作業も含めてすべて PR 経由で行う。使っていない `scripts/dev/merge-to-master.sh`
  （ローカルでマージした `master` を直接 push する）は削除し、ブランチ保護に例外（bypass）を置かない。

## User Scenarios & Testing *(mandatory)*

### User Story 68 - 開発用リポジトリを訪れた人を公開用リポジトリへ案内する (Priority: P1)

開発用リポジトリを訪れた人は、README の冒頭の注記で、ここが開発用であることと、アプリの入手先が公開用リポジトリであることを知る。
公開用リポジトリの README には、この注記は現れない。

**Why this priority**: 公開すると、開発用リポジトリが検索やリンクから見つかる。アプリを使いたい人が、仕様や運用の文書が並ぶ
開発用リポジトリで迷わないようにする。

**Independent Test**: 一時リポジトリで、注記を含む README を書き出し、公開先の README から注記と範囲の印が消え、
ほかの行が変わらないことを確かめる。

**Acceptance Scenarios**:

1. **US68-AS1**: **Given** 開発用リポジトリの README（英語版と日本語版）、
   - **When** 訪れた人が開く、
   - **Then** 冒頭に、開発用リポジトリであることと、公開用リポジトリへのリンクを含む注記が表示される。
2. **US68-AS2**: **Given** 注記を含む README、
   - **When** 公開用に書き出す、
   - **Then** 公開先の README には注記も範囲の印も含まれず、注記を置く前の README と同じ内容である。
3. **US68-AS3**: **Given** 範囲の印の対応が崩れた README（開始だけ、終了だけ、順序が逆、入れ子）、
   - **When** 公開用に書き出す、
   - **Then** 公開先への同期の前に失敗し、公開先は変わらない。

### User Story 69 - PR の最新の head を CI で検証してからマージする (Priority: P1)

保守者は、PR に push するたびに自動で動く CI の結果を見て、最新の head が検証されたことを確かめてからマージする。

**Why this priority**: 今は PR の作成時と Ready にしたときにしか CI が動かず、最後の push が CI を通らないままマージ
されることがある（最近の 8 件のうち 5 件）。公開すると macOS を含む標準ランナーが無料になり、節約する理由がなくなる。

**Independent Test**: PR に追加のコミットを push し、CI が自動で動いてその head の結果が PR に表示されることを確かめる。

**Acceptance Scenarios**:

1. **US69-AS1**: **Given** 開いている PR、
   - **When** 作業ブランチに追加のコミットを push する、
   - **Then** CI が自動で動き、push した head を検証する。
2. **US69-AS2**: **Given** 前の push の CI が実行中の PR、
   - **When** さらに push する、
   - **Then** 古い実行は取り消され、最新の head の実行だけが結果を残す。
3. **US69-AS3**: **Given** CI が失敗した PR、
   - **When** Agent が原因を直して push する、または一時的な失敗の再実行が要る、
   - **Then** Agent は保守者の許可を待たずに、push による自動の実行または再実行で確かめる。

### User Story 70 - 公開後にブランチ保護を設定する (Priority: P2)

保守者は、運用手順に従って、公開した開発用リポジトリの `master` にブランチ保護と必須チェックを設定し、外部の fork からの
PR の workflow を承認制にする。

**Why this priority**: 人の確認だけに頼っていたマージの関門を、GitHub の設定でも守る。設定は保守者しかできないので、
手順が正確であることが要る。

**Independent Test**: 運用手順だけを読んで、保護の設定項目、必須チェックの名前、fork の workflow の承認の設定を
答えられることを確かめる。公開後に、CI が成功していない PR でマージのボタンが無効になることを確かめる。

**Acceptance Scenarios**:

1. **US70-AS1**: **Given** 公開した開発用リポジトリ、
   - **When** 保守者が運用手順に従って `master` の保護を設定する、
   - **Then** 保守者を含めて、PR を経由しない `master` の更新、強制 push、ブランチの削除が拒否され、
     必須チェックが成功していない PR はマージできない。
2. **US70-AS2**: **Given** 必須チェックを設定した `master`、
   - **When** 保守者が自分の PR をマージする、
   - **Then** 承認レビューなしでマージできる。
3. **US70-AS3**: **Given** 外部の貢献者が fork から PR を作った、
   - **When** CI が動こうとする、
   - **Then** 保守者が承認するまで workflow は動かず、動いても workflow のトークンは読み取りだけを持つ。

### 既存のシナリオの変更

#### User Story 28 - CI の結果を読んで Cloud で修正を進める（変更）

- **Independent Test（変更）**: 意図的にビルドを失敗させた PR で、Agent が CI のログから原因を特定し、修正を push し、
  push で自動に動いた CI で再確認できることを確認する。
- **US28-AS2（変更）**: **Given** 追加のコミットを push した、
  - **When** CI が自動で動いて完了する、
  - **Then** Agent は最新の head の成否を確認し、失敗ならログを読んで原因を判断する。

#### User Story 29 - 保守者だけがマージと完了を決める（変更）

- **Why this priority（変更）**: Agent がマージや完了を決めると、保守者のローカルでの確認（起動スモークなど）を
  経ずに変更が `master` に入る。ブランチ保護は CI の成功を確かめるが、ローカルでの確認は人が行う。

#### User Story 30 - ローカル運用と共存する（変更）

- **Independent Test（変更）**: ローカルのセッションで、従来の手順（feature ブランチ、ローカルの検証ゲート）を実行し、
  作業ブランチを push して PR で `master` に統合できることを確認する。

#### User Story 61 - 開発用の CI を公開から除く（変更）

- **US61-AS4（変更）**: **Given** 開発用リポジトリ、
  - **When** PR を作る、Ready にする、PR に push する、または手動で実行する、
  - **Then** 開発用の CI が動く。

### Edge Cases

- **EC-215**: README の範囲の印の対応が崩れている場合（開始だけ、終了だけ、順序が逆、入れ子、複数の範囲）、
  書き出しは公開先への同期の前に中止する。
- **EC-216**: README に範囲の印がない場合、書き出しは README を変えずに続ける。
  - 開発用リポジトリの README に注記があることは、書き出しの検査では確かめない（US68-AS1 の確認に任せる）。
- **EC-217**: workflow 全体がファイルの種類などの条件でスキップされると、必須チェックが待ちのまま残り、マージできなくなる。
  - 開発用の CI には、変更されたファイルによる実行の条件を付けない。
- **EC-218**: 必須チェックにしたジョブの名前を変えると、保護の設定が古い名前を待ち続ける。
  - 名前を変えるときは、同じ PR の作業として保護の設定も更新する（運用手順に示す）。
- **EC-219**: 完了した feature、バグの記録、振り返りにある「非公開」と `merge-to-master.sh` の記述は、当時の記録として変えない。
- **EC-220**: 保守者がローカルから `master` へ直接 push すると、ブランチ保護で拒否される。
  - ローカルで作った変更も、作業ブランチを push して PR で統合する。
- **EC-134**: 削除。開発用リポジトリが公開され、macOS を含む標準ランナーの使用が無料になったため。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-313**: 開発用リポジトリの README は、英語版と日本語版の冒頭に、開発用リポジトリであることと公開用リポジトリ
  （`yoshidax/folzio`）へのリンクを含む注記を置かなければならない。
  - 注記は、開始と終了の印で範囲を示す。
  - 英語版と日本語版は、同じ構造の注記を持つ（README の同期の検査を通る）。
- **FR-314**: 公開書き出しは、README の注記の範囲を、開始と終了の印を含めて除かなければならない。
  - 終了の印の直後の空行 1 行も除き、注記を置く前の README と同じ内容にする。
  - それ以外の行は変えない。
  - 対象は、英語版と日本語版の README である。
- **FR-315**: 公開前の検査は、書き出した README に範囲の印が残る場合と、印の対応が崩れている場合（EC-215）に、
  公開先への同期の前に中止しなければならない。
- **FR-316**: 書き出しの回帰検証は、注記の範囲の除去、範囲の外の行が変わらないこと、印がない README、
  印の対応が崩れた README での同期前の停止を確かめなければならない。
- **FR-317**: 開発用リポジトリの文書・エージェント向けの規約・設定・現行の仕様は、開発用リポジトリを非公開とする前提の
  記述を含んではならない。
  - 「公開する」「公開される」は、公開用リポジトリへの書き出しを指す場合、そのことが分かる書き方にする。
  - 公開用リポジトリへ書き出すファイル（`docs/`・README・ソースのコメント）から、書き出さないファイルへリンクしない規則は維持する。
  - 完了した feature、バグの記録、振り返りは対象外とする（EC-219）。
- **FR-318**: `master` のブランチ保護の運用手順は、保守者が公開後に設定する項目を示さなければならない。
  - PR を経由するマージ、必須チェック（開発用の CI のジョブ）の成功、強制 push とブランチの削除の禁止。
  - 承認レビューは必須にしない。
  - 保護の例外（bypass）の対象を置かない。
  - 外部の貢献者の fork からの PR の workflow は、保守者の承認の後に動かす。
  - 必須チェックの名前を変えるときの手順（EC-218）。
- **FR-319**: 開発用の CI の workflow のトークンは、読み取りの権限だけを持たなければならない。
- **FR-321**: `master` への統合は、ローカルの作業も含めて PR のマージだけで行わなければならない。
  - ローカルでマージした `master` を直接 push するスクリプト（`scripts/dev/merge-to-master.sh`）と、その手順・権限設定の規則は削除する。
- **FR-320**: Agent の権限設定（Claude Code・Codex・Kilo Code）と規約は、CI の起動・再実行を、保守者の許可を求める操作に
  してはならない。
  - CI の起動・再実行に費用の制約があることを前提にした記述を含まない。
- **FR-190（変更）**: Cloud ではビルドとテストを CI で確認しなければならない。
  - CI は PR の作成時、Ready にしたとき、PR への push のたびに自動で動き、最新の head を検証する。手動でも実行できる。
  - Agent は、CI の再確認のための起動・再実行を、保守者の許可なしに行ってよい。
  - Agent は CI の失敗をログから判断し、同じ原因の失敗を 3
    回直しても解決しない場合は作業を止めて報告しなければならない。
- **FR-194（変更）**: ローカル運用（ローカルでの feature ブランチ、ローカルの検証ゲート、worktree による並列実装）は
  維持しなければならない。
  - `master` への統合は、ローカルでも PR 経由で行う（FR-321）。
  - Cloud 用の規則はこれらと区別して定め、互いに矛盾してはならない。
- **FR-176（変更）**: 開発専用のファイルや履歴を配布物へ含めず、アプリにネットワーク機能を追加しない。
  - 既存の公開時の除外・テストを維持する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-166**: 公開書き出しの README（英語版と日本語版）に、注記の範囲の行と印が 0 件で、
  注記を置く前の README との差分が 0 件である。
- **SC-167**: 開発用リポジトリの現行の文書・規約・設定・仕様（完了した feature、バグの記録、振り返りを除く）で、
  開発用リポジトリを非公開とする前提の記述が 0 件である。
- **SC-168**: 公開と保護の設定の後にマージされた PR のうち、最新の head の CI が成功していないものが 0 件である。
- **SC-169**: 保守者が運用手順だけを読んで、ブランチ保護の設定項目、必須チェックの名前、fork の workflow の承認の設定を
  正しく答えられる。
- **SC-093（変更）**: ローカルの従来の手順（feature ブランチ、検証ゲート）と PR による統合が、この feature の前と同じ結果で動く。
- **SC-156（変更）**: 開発用リポジトリの CI が、PR の作成時・Ready にしたとき・PR への push のたびに自動で動き、
  手動でも実行できる。

## Assumptions

- **A-196**: 保守者は、この feature の PR より前に開発用リポジトリを公開する。
  - そのため、この PR の CI は公開リポジトリの条件（標準ランナーは無料）で動く。
- **A-197**: ブランチ保護、fork の workflow の承認、リポジトリの公開は、GitHub の設定で保守者が行う。
  - Agent はこれらの設定を変更できない。
- **A-198**: Claude Code の権限設定（`.claude/settings.json`）は Agent が編集できず、変更は保守者が行う。
  - 変更は新しいセッションから効く（A-109）。
- **A-106（変更）**: 開発用リポジトリは公開リポジトリで、macOS を含む標準ランナーの使用は無料である。
  - 修正は、ログを読んで原因をまとめてから push する。
- 範囲外: リポジトリの公開の操作、ブランチ保護の設定の操作、TAK-32 のリモートブランチ（`agent/019-filter-macos-ci`）の削除、
  履歴の書き換え。
