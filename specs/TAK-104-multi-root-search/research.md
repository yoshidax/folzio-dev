# Research: 複数の検索起点

## R1 起点の指定の UI

- **Decision**: 1〜10 行の起点の行を縦に並べる。各行は既存の起点欄（`NSTextField`）・「選択…」・「削除」（`NSButton`）。一覧の下に
  「起点を追加」を置く。行は `NSStackView` に追加・削除し、シートの高さは Auto Layout で行数に合わせて伸縮させる。
- **Rationale**: 行ごとに既存の欄を使うと、直接入力の解釈（`SearchRoot.parse`）・GUI 選択の文字どおりの扱い（`SearchRootInput.picked`）・
  標準パネルの初期位置（`SearchFolderInitialLocation`）・キーボードの規則（FR-141〜FR-144（search.md））を行単位にそのまま使える。
  10 行（1 行 約 28pt）でもシートの高さは 約 600pt で、1280×800 ポイントの画面に収まる（SC-252）。
- **Alternatives considered**:
  - 1つの欄に区切り文字で並べる: `;`・`,`・改行はフォルダ名に使えるため曖昧で、末尾の空白を保つ規則（US16-AS10）も表せない。
  - `NSTableView` の一覧と ＋／− ボタン（Finder の検索条件の行の風）: 表の中の編集と GUI 選択の結果の反映・Tab の移動が複雑になる。
    10 行程度なら行のビューを並べる方が単純。
  - 標準パネルの複数選択で一度に追加: 行と選択の対応が分かりにくく、FR-141 の構成を変える必要がある。

## R2 起点の整理（重複と重なり）

- **Decision**: 検証（`SearchRoot.validate`。シンボリックリンクを解決したパスを返す）の後のパスで整理する。
  1. `SearchPath.normalized` が同じものは最初の1つを残す（EC-300）。
  2. 起点 C が別の起点 P の配下（`SearchPath.isSameOrWithin`）にあるとき、P の直下から C までの各階層（C 自身を含む）について、
     名前が `.` で始まるか `isHidden` が真、または `isPackage` が真のものがなければ C を除く（EC-301）。あれば残す（EC-302）。
  3. 残った起点は、入力の行の順（同じものは最初の行の位置）に並べる。
- **Rationale**: `FileNameSearcher` は `.skipsHiddenFiles`・`.skipsPackageDescendants` で列挙し、シンボリックリンクのフォルダを辿らない。
  検証後のパスはリンクを解決済みなので、P の配下にあることは実際の階層の包含を意味する。間の階層に隠しフォルダ・パッケージがなければ、
  P の列挙は C とその配下を必ず辿るので C は不要。あれば P は C の配下に入らないので、両方を辿っても重複しない。
  C 自身が隠しフォルダ・パッケージの場合も P の列挙は C を辿らない（パッケージは起点の検証で弾かれる）ので、C を残す。
  属性の読み取りは配下の起点ごとに間の階層の数だけで、UI のスレッドの外で行う。属性の読み取りは閉じた関数として注入し、
  テストでは仮の属性で全分岐を確かめる。
- **Alternatives considered**:
  - 起点を整理せず、結果の URL で重複を除く: 同じ場所を2回辿るので時間が倍になり得る（SC-249 に反する）。`/private/var` と `/var` の
    ような表記の違いで重複を見落とす恐れもある。
  - 配下の起点を常に除く: 隠しフォルダの配下を明示した起点（FR-083 の既存の規則）が検索されなくなる。

## R3 複数の起点の辿り方

- **Decision**: 整理した起点を上から1つずつ順に `FileNameSearcher.search(_:)` で辿る。1つの起点の列挙の終わりに次の起点の列挙を始め、
  最後の起点の終わりで `phase = .finished` にする。検索を止める操作は、実行中の列挙を止め、待ち行列を捨てる。
- **Rationale**: 同じボリュームの起点を同時に列挙すると読み取りが競合し、合計の時間が単一の起点より悪くなり得る（A-266）。
  順に辿れば合計の読み取り量と時間は1つの階層の検索と同じで、既存の SC-016・SC-054 の枠に収まる。
  既存の `startSearchStream` は列挙ごとに `SearchVisitLog` を作って台帳（`SearchRenameLedger`）に登録し、`activeSearchStreams` で
  完了を数える。起点ごとの列挙をこの仕組みで順に登録すれば、名前の変更の台帳の意味（列挙の開始時点の名前の変更の数）が保たれる。
- **Alternatives considered**:
  - すべての起点を同時に列挙: 上の理由で採らない。別のボリュームどうしの並行は速くなり得るが、ボリュームの判定と測定が要るため範囲外（A-266）。
  - `SearchRequest` に起点の配列を持たせ、1つの列挙の中で順に辿る: 起点ごとに異なる表記の補正（`rebaser`）と記録を1つのストリームで
    扱うことになり、名前の変更の台帳の「列挙の開始時点」が起点ごとにずれる。

## R4 起点ごとの名前の変更・削除・変更通知

- **Decision**:
  - 名前の変更（`didRenameFolder`）: 整理した起点の各々に既存の判定（起点そのもの・祖先なら新しい起点を辿り直し、配下なら新しい場所だけを
    追加で辿る）を当てる。ただし、まだ列挙を始めていない起点（待ち行列にある起点）については、起点のパスだけを新しい名前に置き換え、
    追加の列挙も台帳への記録もしない。その起点の列挙は、始めた時点の名前で辿るため。
  - 削除・移動（`pruneMissingResults`）: `SearchRemovalScope.topmostMissing` に渡す起点を、その結果を含む起点（下の R5 の
    「含む起点」）にする。起点そのものが消えたときは、その起点の配下の結果だけを外す（EC-306）。待ち行列にある起点が消えた場合は、
    列挙を始めたときに列挙できず、結果が増えないだけで済む（既存の `enumerator` が `nil` のときと同じ）。
  - 変更通知: `DirectoryTreeViewController.updateWatchSet` の `subtrees` を、検索中・表示中のすべての起点にする。
- **Rationale**: 既存の規則を起点ごとに適用する（FR-440）ことで、新しい判定を増やさずに済む。待ち行列の起点に既存の「配下の名前の変更」
  の規則を当てると、追加の列挙と、後で始まるその起点の列挙が同じ場所を2回辿り、結果が重複する（Complexity Tracking）。

## R5 「場所」列と検索バー

- **Decision**:
  - 項目を含む起点: 整理した起点のうち、項目の URL を含む（`SearchPath.isSameOrWithin`）もので、パスが最も長いもの。EC-302 の入れ子では
    内側の起点になる。
  - 「場所」列: 含む起点のフォルダ名（ルートは絶対パス）＋相対パス。含む起点のフォルダ名がほかの起点のフォルダ名と同じなら、起点の
    絶対パス＋相対パスにする（EC-305）。フォルダ名の比較は大文字小文字を区別しない（APFS の既定に合わせ、見分けにくいものを避ける）。
  - 検索バー: 起点が1つなら従来の文字列。2つ以上なら、既存の文の `{フォルダ名}` の位置に「{最初の起点のフォルダ名} ほか {n} か所」を
    入れる。ツールチップは、表示中の文の後に改行して全起点の絶対パスを1行ずつ並べる。
- **Rationale**: 既存の文言（`searchBarResults`・`searchBarSearching`）の差し込み位置を使えば、文の構造と翻訳を変えずに済む。
  ツールチップに文そのものを残すのは、幅が狭いときに切れた文を読めるようにする既存の目的（R37 の時点の実装）を保つため。

## R6 ワイルドカードの説明

- **Decision**: キーワード欄の直下に、補足説明（FR-394）と同じ `NSTextField(wrappingLabelWithString:)`・`.small` のシステムフォント・
  `secondaryLabelColor` のラベルを置く。キーワード欄の `accessibilityHelp` は「補足説明 + 空白 + ワイルドカードの説明」にし、
  ラベル自身は `setAccessibilityElement(false)` で読み上げの項目にしない（既存の補足説明と同じ扱い）。
- **Rationale**: 既存の補足説明の作り方と表示・読み上げの規則（FR-394）にそろえる。プレースホルダは前回のキーワードが入ると見えない（A は Clarifications）。

## R7 検証の失敗の示し方

- **Decision**: 既存の理由のラベル（`reasonLabel`）を起点の行の一覧の下に1つだけ置き、行が2つ以上のときは
  「{n} 番目の検索起点: {理由}」（英語: `Folder {n}: {reason}`）を表示・読み上げる。その行の起点欄にフォーカスを移す。
  `SearchPanelInputState` の完了の判定（revision・requestGeneration）を行の追加・削除にも適用し、古い検証の結果を捨てる。
- **Rationale**: 行ごとにラベルを置くとシートの高さが変わりやすく、読み上げも分散する。既存の1つのラベルと読み上げの仕組みを使う。
