## 目視の確認（保守者、GUI）

### 準備

大きな画像（例: 24 メガピクセル以上の JPEG）を 30 枚以上入れたフォルダと、同様の画像を入れた zip を用意する。

### シナリオ 1: 通常の画像の連続送り（US57）

1. `open .build/Folzio.app` で起動し、フォルダを開いて先頭の画像を選ぶ
2. ↓ キーを数秒間押し続けて画像を連続して送り、離す
3. 期待: アプリが固まらず、離した後に最後の画像が表示される。途中の画像が後から表示に割り込まない
4. Activity Monitor で Folzio のメモリを見て、送っている間に極端に増え続けない（目安。数値の基準は設けない）

### シナリオ 2: zip の中の画像の連続送り（US58）

1. zip を開いて先頭の画像を選び、シナリオ 1 と同じように連続して送る
2. 期待: シナリオ 1 と同じ。zip から出てフォルダに戻っても、すぐに画像を選んで表示できる

### シナリオ 3: 通常の操作（US59）

1. 画像を 1 枚ずつ ↓ で送る
2. 期待: 先読み済みの画像は一瞬で切り替わる。初めて開く大きな画像も、従来と体感で変わらない時間で表示される

## 結果の記録

### シナリオ 1 のメモリの計測（2026-11-03、保守者の報告による）

- 条件: サムネイル形式。画像の平均は約 500 KB、ディスプレイは 1920×1080。起動し直してから約 0.3 秒間隔で 30 回ほど送り、`footprint -p Folzio` で計測した。
  環境は MacBook Air 13 インチ（M3、2024）、メモリ 16 GB、macOS 26.6.2。操作の間隔は手動で、回ごとに揃っていない
- 値は各ビルドで 3 回（MB）。master は 9a5d9cc 相当のビルド

| 計測 | TAK-15 | master |
|---|---|---|
| Footprint | 783 / 805 / 799 | 790 / 776 / 795 |
| ピーク（phys_footprint_peak） | 845 / 879 / 934 | 864 / 918 / 864 |
| CoreAnimation | 259 / 249 / 249 | 249 / 249 / 249 |
| CG raster data | 240 / 235 / 235 | 235 / 235 / 235 |
| MALLOC_LARGE | 188 / 240 / 233 | 222 / 213 / 230 |

- 判断: Footprint もピークも範囲が重なり、master との差は見られなかった（この計測の範囲では、悪化も改善も言えない）。最初の 1 回ずつの計測で見えた約 100 MB の差は、
  計測のばらつきの範囲だった
- メモリの大半は CoreAnimation（約 250 MB）と CG raster data（約 235 MB。プレビューのキャッシュ上限 256 MB に近い）で、master と同じ。この feature が目標にした
  同時デコードの一時バッファは、この条件では主要な割合ではなかった（原因の特定はしていない）
- 200〜300 枚を続けて送っても、メモリは 1 GB 未満で頭打ちになった（保守者の報告。値は記録していない）。上限のない増加（リーク）の形ではなかった
- 速いキーリピートでは、プレビューが表示される前に次へ移るため、メモリは増えにくかった（保守者の報告）
- シナリオ 2（zip の中の画像の連続送り）と 3（1 枚ずつの通常の操作）、およびローカルの最新 Swift での `swift build` と `swift test` は、
  保守者が確認し、問題なしと報告を受けた（2026-11-03。確認の環境や件数などの詳細は報告を受けていない）
- メモリ全体の削減（CoreAnimation の内訳の調査、キャッシュ上限の見直し）は、この feature の範囲外として別の Issue で扱う
