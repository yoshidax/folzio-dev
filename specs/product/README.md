## ID の付け方

- 各領域のファイルにある項目は、次のラベルを持つ。1つのラベルは1つのファイルだけで定義し、ほかの領域からは ID で参照する
  - `FR-xxx`（機能要件）・`SC-xxx`（成功基準）: 新しい ID は全領域を通した最大値の次の番号にする
  - `USn-ASm`（受け入れシナリオ）・`EC-xx`（エッジケース）・`A-xx`（前提）: 001 の spec.md での位置を示す。
    - 新しく追加するものも同じ形式で、全領域を通した最大値の次の番号にする
- 項目を削除しても ID は再利用しない
- ID が衝突した場合は、[仕様 ID の重複解消](../../docs_private/spec-id-conflicts.md)に従う

## 更新の流れ

1. 新しい要件は、`/speckit-specify` で新しい feature ディレクトリ（`specs/NNN-xxx/`）を作って扱う。
   - 同じ名前の feature ブランチは、git 拡張の `before_specify` フックが今の HEAD から切る（クリーンな master
     から始める）。
   - その spec.md には変更点（追加・変更・削除する項目）だけを書き、関係する既存の項目はこのディレクトリの ID
     で参照する
2. plan・tasks・実装・converge は、その feature ディレクトリで行う
3. 実装と検証が終わったら、変更点をこのディレクトリの該当する領域のファイルへ反映し、feature ディレクトリは凍結する

完了した feature ディレクトリ（`001-three-pane-media-viewer` など）の plan.md・research.md・tasks.md は、
実装の経緯の記録として残す。

## feature の spec.md の書き方

- 節立ては Spec Kit のテンプレートのまま使い、各節には変更点だけを書く
- 追加する項目は新しい ID で書く。
  - 既存の項目を変える場合は、同じ ID で変更後の全文を書き、見出しに「（変更）」と付ける。
  - 削除する場合は ID と理由だけを書く
- 既存の項目を参照するときは、ID と領域のファイルを書く（例: `FR-084（search.md）`）
- 末尾に「## 反映先」の表を置き、追加・変更・削除する項目ごとに反映先の領域のファイルを書く

  | ID | 種別 | 反映先 |
  |---|---|---|
  | FR-099 | 追加 | search.md |
  | FR-084 | 変更 | search.md |

- 反映するときは、決定後の本文だけを領域のファイルへ移す。`## Clarifications` のセッションログは feature 側に残す
- 反映が終わったら、feature の spec.md の冒頭に、001 と同じ形式で移行済み・凍結の注記を入れる

## 書き方のルール

領域のファイルと契約は、差分を読みやすく保つため、次のように書く。
`scripts/dev/check-spec-format.py` で確かめる（「形式の検査」）。

- 1つの箇条書きには、1つの要件・条件・例外を書く
  - 条件と例外は、本文に続けず、子項目に分ける
  - ID の定義（`FR-xxx`・`SC-xxx`・`EC-xx`・`A-xx`・`USn-ASm`）の本文は、1文にする
- 表のセルは短い要約にする（表示幅 80 桁以内）
  - 詳細は、表の直後の `**表の詳細**` の下に箇条書きで書き、セルには `下記` と書く
  - `**表の詳細**` の各項目は `- **キー**（列名）: 本文` の形で始め、キーは表の行の最初の列と同じ文字列で始める
  - 1つの表の行は、物理的に1行で書く。列数をそろえ、2行目に区切りの行を置く
- 次のものは、途中で改行しない
  - インラインコード（`` ` `` で囲んだパスやコマンド）
  - 引用（「」・“ ”）。メニュー名・ボタン名・UI の文言など
  - 英語の語句（`Sentence case` など）
- 1行の表示幅は 120 桁以内を目安にする
  - 改行は、上の途中で改行しないものの前後で行う
  - 引用そのものが長く 120 桁に収まらない場合は、引用を1行に置く（警告になるが、引用を折るより優先する）

## 形式の検査

```bash
python3 scripts/dev/check-spec-format.py
python3 scripts/dev/check-spec-format.py --update-baseline
python3 scripts/dev/check-spec-equivalence.py origin/master
```

- `check-spec-format.py` は、`specs/product/` 以下の Markdown を調べ、崩れを行の番号とともに表示する
- エラーは、1件でもあれば失敗する
  - 160 桁を超える行
  - 物理的に複数行にまたがる表の行、列数が揃わない表、区切りの行がない表、本体の行がない表
  - 行をまたぐインラインコード・引用・英語句
  - `下記` に対応する「表の詳細」の項目がない行
- 警告は、ファイルと検出項目ごとの件数が、基準値（`scripts/dev/spec-format-baseline.json`）を超えたときだけ失敗する
  - 120 桁を超える行、80 桁を超えるセル、2つ以上の文を含む ID の定義
  - 警告が減ったときは、`--update-baseline` で基準値を更新する
  - 増えた警告を直せない場合は、理由を PR に書いて基準値を更新する
- 表示幅は、East Asian Width が W（全角）または F（全角英数）の文字を 2 桁、
  それ以外（A（曖昧）を含む）を 1 桁として数える
  - 行頭のインデントを含め、行末の空白は含めない
- コードブロックの中は調べない
- 英語句の分断は、前の行の末尾が英字で、続きの行が英小文字で始まるときに検出する
- `下記` の行は、`**表の詳細**` の項目のうち、見出し（`**…**`）がその行のキーで始まるものと対応づける
  - 同じキーの行が複数ある場合は、見出しにキーに続けて区別を書く（例: `**ファイル操作 / 補足説明**`）
- 検出の対象外は、`scripts/dev/spec-format-config.json` の `exclusions` に、
  ファイル、範囲、検出項目、理由を書いて指定する
  - 範囲は `section`（見出しの行と同じ文字列。次の同じかより上位の見出しまで）で指定する
  - または `table_columns`（見出しの行に含む列名）で表を指定する。どちらもなければファイル全体とする
  - 対象外の指定が何にも当たらないときは、設定の誤りとして終了コード 2 で止まる
  - 今の指定は、`overview.md` の「出発点となった要望」の引用と、`contracts/localization.md` の対訳表のセルの幅
- `check-spec-equivalence.py` は、形式だけを変える変更（改行の位置、子項目への分割、表から「表の詳細」への移動）で、
  本文が変わっていないことを確かめる
  - 指定した版と HEAD の共通の祖先にある `specs/product/` と、作業ツリー（コミットしていない変更を含む）を比べる
  - 空白・箇条書きと見出しの記号・強調・表の区切り・句読点（`。`・`、`・`,`）と、「表の詳細」の形式の印（`下記` のセル、
    `**表の詳細**` の行、見出しのうち表の行のキーと重なる部分、見出しの直後の括弧）を除いて、文字単位で比べる
  - 「移動」「追加」「削除」を一覧にする。「追加」と「削除」がなければ成功する
  - 移動と子項目への分割で、係り受けや文脈が変わっていないかは、一覧を人間が読んで確かめる
