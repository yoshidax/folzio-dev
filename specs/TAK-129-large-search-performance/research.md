# Research: TAK-129 の検索の性能

調査の基準: `origin/master`（dd43232）。Cloud では Swift を実行できないので、計測は CI の性能テストの記録と、コードの読み取りによる。

## R1 現状の計測（CI の記録）

- 記録: macOS Swift CI の run 43393666034（2026-11-13、master の 1d88b66、`macos-15`、debug ビルド）の性能テストのログ
  - `[perf] batch 256 into 50,000: 0.11015975 seconds`（`processingBatchIntoFiftyThousandWithinBudget`。基準 100ms を超えて失敗）
  - `[perf] merge 256 into 10,000: sortedMerge 0.013737917 seconds, BrowserModel 0.020006625 seconds`
  - `[perf] search 10,000 files: 0.973303375 seconds`（`FileNameSearcher` の列挙だけ。100 フォルダ × 100 ファイル、半分が一致）
- 読み取り:
  - 5万件の一覧への1回の追加は約 0.11 秒で、SC-004 の 100ms を1回で超える。5万件では 256 件か 100ms ごとのまとまりが数百回届くので、
    UI スレッドの合計は 10 秒を超える見込み（1回の時間は件数に比例して増えるため、合計は件数の2乗に近い）
  - 列挙は 1万件で約 1 秒なので、5万件では CI で約 5 秒の見込み。保守者の Mac（release ビルド）では速いが、3 秒の基準（SC-249）に
    余裕はない。列挙も速くする必要がある（R7）
- 未計測: 表示側（`reloadData` とフローレイアウト）の時間、QuickLook の生成の数。GUI なしでは計れないので、R9 の性能テストと保守者の確認で補う

### 実装の前の値（T004）

- 記録: macOS Swift CI の run 46015966072（2026-11-27、7a299f1、`macos-15`、debug ビルド）の性能テストのログ。この run は後の push で
  `cancelled` と表示されるが、通常のテスト（1,400 件成功）と性能テストは最後まで実行されていた
  - `[perf] search 50,000 files: 3.217647334 seconds, matches 25000`（列挙だけ。SC-249 の 3 秒を超える）
  - `[perf] model search 50,000 files: 4.618384041 seconds, rows 25000`（`BrowserModel` から検索して一覧が確定するまで。表示側は含まない）
  - `[perf] main thread max gap during 50,000-file search: 0.087228125 seconds`（表示側を含まない `BrowserModel` だけの値）
  - `[perf] batch 256 into 50,000: 0.075336416 seconds`（並べ替えて合流する1回の処理。SC-253 の 50ms を超える）
- 読み取り: 列挙だけで 3 秒を超えるので、列挙を速くすること（R7）が SC-249 に必要。UI スレッドの空白は `BrowserModel` だけでは
  100ms 未満で、保守者の観察（反応が遅い）の主な原因は表示側（`reloadData`・サムネイルの要求）にあると推定する（未計測）

## R2 検索中の並び順（FR-085（変更）・FR-437）

- Decision: 検索中は並べ替えず、見つかった順に末尾へ足す。検索の終了時に1回だけ並べ替える（保守者の決定、2026-11-27）
- Rationale: 名前順で並べながら足すと、新しい結果が見えている範囲に入り続け、見えている項目と縮小画像の要求が入れ替わり続ける。
  末尾に足すだけなら見えている項目は変わらず、1回の追加は件数に比例しない（FR-436）
- Alternatives considered:
  - 並べ替えを続け、反映をまとめる: 反映の回数は減るが、1回の合流が O(n) のまま（5万件で 0.11 秒）で、見えている項目も入れ替わる
  - 合流の比較を二分探索で減らす: 比較の回数は減るが、配列の作り直しと見えている項目の入れ替わりは残る
  - 並べ替えたまま見えている項目の位置を保つようにスクロールを補正する: 実装が複雑で、先頭に入った結果に気付きにくい

## R3 反映の間隔（FR-085 の 1 秒の上限）

- Decision: `BrowserModel` で、届いたまとまりをため、件数に応じた間隔で反映する（1,000 件未満 0.1 秒、1万件未満 0.25 秒、3万件未満 0.5 秒、それ以上 1 秒）。
  最初の結果はすぐに、ストリームの終わりでは待たずに処理する
- Rationale: 末尾への追加でも、表示側の差分の挿入とレイアウトは件数に応じて重くなる。件数が少ないうちは従来どおりすぐに出し、
  多くなったら回数を減らす。上限の 1 秒は FR-085 の遅れの上限
- Alternatives considered: `FileNameSearcher` の `batchInterval` を変える（列挙側が UI の件数を知らないので、件数に応じて変えにくい）

- **実装中の修正（2026-11-27）**: 最初の実装では、届いたまとまりをためておき、反映の時刻にまとめて処理した（索引への登録・種類の名前・
  `allFiles` への追加）。CI の性能テスト（run 46020819649、5a19af7）で、UI スレッドの最大の空白が 462ms（実装の前は 87ms）に悪化した。
  1 秒分（1万件以上）を一度に処理したためと推定し、結果ごとの処理は実装の前と同じく届くたびに行い、画面の一覧への反映だけを
  まとめる形に直した（`unlistedSearchResults`。一覧を作り直すと 0 に戻す）

## R4 終了時の並べ替えを UI スレッドの外で行う

- Decision: 終了時と、検索中の並べ替えの列・向きの変更では、`allFiles` の写しを `Task.detached` で並べ替え、UI スレッドで `kindFilesRevision`
  が変わっていなければ適用する。変わっていればやり直す（`setKindNames` の既存の形）
- Rationale: 5万件の自然な順（`localizedStandardCompare`）の並べ替えは約 80 万回の比較で、UI スレッドでは 100ms を超える見込み（R1 の
  1万件の合流 14ms から推定）。版の照合で、並べ替えの間の名前の変更・削除を失わない
- Alternatives considered: UI スレッドで並べ替える（簡単だが SC-251 を満たさない見込み）

## R5 表示側の差分の挿入

- Decision: 新しい URL の列が前の列で始まるなら、`NSCollectionView.insertItems(at:)`・`NSTableView.noteNumberOfRowsChanged()` で末尾だけを足す
- Rationale: `reloadData` は見えている項目を作り直し、縮小画像を要求し直す。末尾に足すだけなら見えている項目は変わらない
- 判定の費用: 前の列との比較は O(n) の URL の比較だが、反映は最大 1 秒ごとなので、5万件でも数 ms の見込み。計測で重ければ、
  `BrowserModel` が「末尾に足した件数」を世代とともに渡す形に変える
- フローレイアウト: 全項目が同じ大きさなので、`sizeForItemAt` を `itemSize` に置き換え、項目ごとの問い合わせをなくす。
  大きさは、サムネイルの大きさとペイン幅の変更時に更新する（今 `invalidateLayout` している箇所）
  - **取りやめ（2026-11-27、実装中）**: 置き換えると、既存の App のテスト「A thumbnail successor below the viewport is revealed without
    changing the first responder」が失敗した（CI run 46018851463、job 140573060492。実装の前の run 46015966072 では 0.07 秒で成功）。
    一覧の幅が `updateCollectionViewFrame` を通らずに変わると `itemSize` が更新されず、項目が1行に詰まってスクロールしなくなったと
    推定する。計測なしの最適化で、通常のフォルダの表示を変えない（A-269）ことを優先し、`sizeForItemAt` に戻した

## R6 検索中の縮小画像の要求（FR-435・SC-252）

- Decision: 検索中は `prefetchItemsAt` で要求しない。一覧が変わったら、見えている項目以外の要求を取り消す。検索の終了で並べ替えた後は、
  見えている項目を要求し、先読みを再開する
- Rationale: 今は、一覧から消えた URL の要求だけを取り消す（`pruneRequests`）。先読みで要求した項目が画面外へ押し出されても、
  `cancelPrefetchingForItemsAt` が呼ばれなければ要求が残る。zip の外の QuickLook の生成には、アプリ側の同時実行数の上限がない
- 通常のフォルダの先読み・同時実行数は変えない（A-269）。QuickLook に上限を設ける案は、通常のフォルダの SC-003 に影響するので採らない

## R7 列挙を速くする

- Decision:
  - 列挙で、行に使う属性（作成日・変更日・サイズ・`FileContentVersion.resourceKeys`）も `includingPropertiesForKeys` で前もって読む
  - 種類の名前（`localizedTypeDescriptionKey`）は、1回の検索の中で拡張子（小文字）ごとに1回だけ読む
- Rationale: 今は一致したファイルごとに `resourceValues(forKeys:)` を呼び、種類の名前の問い合わせ（UTI と LaunchServices）を毎回行う。
  対応するメディアの判定は拡張子による（FR-039）ので、同じ拡張子の種類の名前は同じになる
- リスク: 前もって読む属性は、一致しないファイルの分も読む。一致が少ない検索で遅くならないか、SC-016・SC-054 の性能テストで確かめる。
  遅くなれば、前もって読む属性を元に戻し、種類の名前のキャッシュだけにする

## R8 並行する作業との競合

- TAK-104（複数の検索起点、進行中）は、起点ごとに `startSearchStream` を呼び、すべての列挙の終了で検索を終える（`activeSearchStreams`）。
  本 feature の終了時の並べ替えは、その「すべての列挙の終了」で行う。どちらが先にマージされても、終了の判定の箇所で合わせる
- TAK-90（フォルダの名前の変更での付け替え）とは、検索中の名前の変更の扱い（EC-304）で関係する。行の位置を動かさない点だけを本 feature で変える

## R10 一度作った縮小画像を表示し直すとき（保守者の確認の後に追加）

- 保守者の報告（2026-11-27、手元）: 検索の終了後、表示範囲の外へ出た項目が戻ると、サムネイルを作り直しているように見える
- 原因（コードの読み取り。手元での再現はしていない）:
  - 作った縮小画像は `ThumbnailProvider` の `NSCache` に保持している（上限 `MemoryLimits.thumbnailCacheBytes` = 128MB）。
    既定のサムネイルの大きさ 128pt を Retina で表示すると 1 枚は最大 256×256 ピクセル（約 256KB）で、約 500 枚を保持できる
  - しかし、項目の部品が別のファイルに使い回されると、`ThumbnailItemView.configure` はまず種類のアイコン
    （`NSWorkspace.shared.icon(forFile:)`）を表示し、`requestThumbnail` で保持している縮小画像を非同期に取り出して差し替える。
    保持していても、アイコンから縮小画像への切り替わりが見える。リスト形式の行頭の縮小画像も同じ作り（`IconCatalog.fallbackIcon`）
  - 通常のフォルダでも同じ作りで、今回の変更による回帰ではない。検索が速くなり、目に付きやすくなったと推定する
- Decision: 保持している縮小画像を同期で引き、あれば種類のアイコンを挟まずに設定する（FR-438）。保持の上限は変えない（保守者の決定）
- Alternatives considered: 保持の上限を広げる（遠くへスクロールしても残りやすいが、メモリを多く使う。保守者が採らないと決めた）

## R11 計測のためのデバッグログ（保守者の確認の後に追加）

- 保守者の報告（2026-11-27、手元）:
  - 検索結果のファイルリストで画像を選んでからプレビューに出るまでが遅い（0.5〜0.8 秒に感じる）。検索の終了後も遅い。結果が少ないときは遅くない
  - サムネイル形式で、ホイールでのスクロールでは表示し直したサムネイルを作り直さなくなったが、スクロールバーのドラッグと、↓キーのリピートでの
    スクロールでは、変更の前と同じく作り直している
- 保守者の決定: 数値で計測してから原因を調べるため、ログを埋め込む。対策はログで状況を把握してから決める
- コードからの仮説（未計測）:
  - プレビュー: 選択の変更で件数に比例する処理（`listing.files.first(where:)`、`firstIndex(where:)`、各ビューの `applyModel` の URL の列の比較）は
    1件あたり軽く、2万5千件でも数十 ms の見込み。デコードとサムネイルの生成（QuickLook）が CPU やディスクを取り合っている可能性もある
  - 作り直し: スクロールバーのドラッグやキーのリピートでは多くの項目を短い時間で通過し、通過した項目のサムネイルも作られて保持の上限
    （128MB）を使い切り、前に見た項目が捨てられる可能性がある。`NSCache` は最後に使った順に捨てるとは限らない（Apple の文書で未確認）
- ログ: subsystem `local.folzio.Folzio`・category `Performance`、debug レベル（保存されず、`log stream` で見るときだけ出る）。
  ファイル名はハッシュで出す。行の頭の印で分ける: `[thumb]`（作成・保持・破棄）、`[list]`（一覧からの要求・取り消し・表示）、
  `[preview]`（選択・デコード・表示）、`[main]`（`applyModel` などの時間と UI スレッドの止まり）

## R9 計測の手順

- 実装の前に、性能テスト（5万件の列挙だけ・`BrowserModel` からの検索の確定まで・UI スレッドの最大の空白）を足し、CI で現状を記録する
- 実装の後に同じテストで比べ、結果を PR に記載する（憲章の原則 II）。CI の性能テストは失敗を許容するステップなので、ログの末尾を読んで確かめる
- 表示範囲の縮小画像がそろうまでの時間（SC-250）と、操作の停止（SC-251）は、保守者の Mac で quickstart.md の手順で確かめる
