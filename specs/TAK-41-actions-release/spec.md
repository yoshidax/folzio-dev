# Feature Specification: リリース PR からソース公開と配布を行う

**Feature Branch**: `agent/tak-41-release-design`
**Local checkout**: `work`（同じコミットを追跡する Cloud のブランチ）
**Created**: 2026-11-06
**Status**: Draft（改訂設計のレビュー待ち）
**Input**: [TAK-41](https://linear.app/takyoshida/issue/TAK-41) と、このチャットの追加要望。
「公開用との分離を維持し、任意のリリース時点で同期とビルドを GitHub 内で行う。
開発用リポジトリで release.json 変更の PR を起点にリリースまで持っていく。
リリース前に同等のコードを CI でビルドした成果物をダウンロードし、ローカル PC で確認する」。

基準は `origin/master` の `03c80bc`。開発用は `yoshidax/folzio-dev` / `master`、
公開用は `yoshidax/folzio` / `main`。関連する正本は
FR-169〜180・FR-289〜295・FR-311〜316（overview.md）、contracts/scripts.md・contracts/app-bundle.md。
前回案のローカル publish を前提にする部分を置き換える。

## User Scenarios & Testing *(mandatory)*

### User Story 74 - リリースする時点を PR で指定する (Priority: P1)

保守者は変更を master に蓄積し、配布したい時点で release.json とノートを変更する PR を作る。
その PR の検証とレビューを終えてマージすると、GitHub 内でソース公開と配布が始まる。

**Why this priority**: 通常の開発更新を公開せず、ローカルの公開作業も不要にする入口。
**Independent Test**: 通常 PR と release.json 変更 PR を比較し、公開先の更新と配布開始の有無を確認する。

1. **US74-AS1**: **Given** 通常の開発 PR、**When** master にマージする、
   **Then** 公開用 main と Release は変わらない。
2. **US74-AS2**: **Given** 有効な release.json 変更 PR、**When** PR を検証する、
   **Then** 公開候補のアプリ ZIP・チェックサム・出自をダウンロードでき、公開用への書き込みは行われない。
3. **US74-AS3**: **Given** 検証済みのリリース PR、**When** master にマージする、
   **Then** CI 候補とマージ済みコミットの公開ツリーが一致する場合に、候補の検証結果を使って1コミットで同期する。
4. **US74-AS4**: **Given** 公開候補の検証に失敗する変更、**When** 同期処理が動く、
   **Then** 公開用 main は更新されず、失敗理由が示される。
5. **US74-AS5**: **Given** 候補の確認後に他の PR が master に入り、実際のマージ結果の公開ツリーが異なる、
   **When** 同期の判定を行う、**Then** そのマージ済み SHA の候補を作り直して確認待ちとなり、
   保守者が取得・ローカル再確認して同じ SHA と run を指定するまで公開しない。

### User Story 71 - 公開コミットから配布ドラフトを作る (Priority: P1)

公開用へ同期されたコミットから、arm64 のアプリとチェックサム付き ZIP を作る。

**Why this priority**: 公開されたソースと実際の配布物を一致させる。
**Independent Test**: 公開用の push と手動実行で、タグ・両バージョン・署名・ZIP・ノートを照合する。

1. **US71-AS1**: **Given** 新しい配布要求を含む公開用 push、**When** 検証が成功する、
   **Then** イベントの公開用コミットを指すタグと ZIP・SHA256SUMS・ノート付きドラフトができる。
2. **US71-AS2**: **Given** 復旧用の同期で配布要求は変わらない、**When** ソースのみ公開用へ更新する、
   **Then** 既存のタグ・Release・配布物は変更しない。
3. **US71-AS3**: **Given** 実行中に開発用または公開用の HEAD が進む、**When** 成果物ができる、
   **Then** 対象は元のイベント SHA に固定される。

### User Story 72 - 失敗を復旧する (Priority: P1)

保守者は GitHub 上で同期と配布を再実行でき、既存データを上書きせず障害に対処できる。

**Why this priority**: 部分失敗でも公開済みの内容を保持する。
**Independent Test**: 無差分、古い候補、同名タグ、既存 Release、API 障害と競合を再現する。

1. **US72-AS1**: **Given** 同期済みの同じ候補、**When** 同期を再実行する、
   **Then** 重複コミットを作らず、必要な配布の再実行先を案内する。
2. **US72-AS2**: **Given** 対象コミットと一致するタグだけがある、**When** 公開用の元の実行を再実行する、
   **Then** タグを動かさずドラフトを作れる。
3. **US72-AS3**: **Given** 別コミットの同名タグまたは既存 Release、**When** 配布を試みる、
   **Then** 既存データを変更せず停止する。
4. **US72-AS4**: **Given** 公開済み候補より古い同期候補または外部の公開先更新、**When** 書き込みを試みる、
   **Then** 巻き戻しや強制更新を行わない。
5. **US72-AS5**: **Given** リリースが M でマージされ、その後 master が M+3 へ進んだ、
   **When** M を明示して候補生成と同期を手動実行する、
   **Then** 両処理は M を使い、起動時点の HEAD や途中で加わった変更を配布に混ぜない。

### User Story 73 - 成果物を確認して公開する (Priority: P2)

保守者はまずリリース PR の CI から確認用 ZIP を取得してローカル PC で試す。
確認した最新候補の PR をマージする。マージ結果が候補と異なるときは、その固定 SHA の新候補を再確認して同期を再開する。
作成されたドラフトの添付物と出自を確認して公開する。

**Why this priority**: ビルド成功だけでは3ペイン・日英表示と Gatekeeper の動作を確認できない。
**Independent Test**: ダウンロードした ZIP をビルド環境外へ展開して起動する。

1. **US73-AS1**: **Given** リリース PR の最新 CI、**When** Actions から確認用成果物を取得する、
   **Then** 手元でビルドせず、ZIP のアプリを展開して日英・3ペイン・バージョンを確認できる。
2. **US73-AS2**: **Given** 自動作成されたドラフト、**When** 内容を確認する、
   **Then** 開発用 SHA・公開用 SHA・タグ・両バージョン・チェックサム・実行元を追跡できる。
3. **US73-AS3**: **Given** 自動検証の成功、**When** 保守者の公開操作はまだない、
   **Then** Release はドラフトのままである。

### Edge Cases

- **EC-221**: 要求が不正、ノートが空・未コミット・symlink・範囲外のパスなら書き込み前に失敗する。
- **EC-222**: push の比較元が読めなければ変更なしと見なさず失敗し、初回の all-zero before は空として扱う。
- **EC-223**: PR・fork・対象外の repo / branch から公開先への書き込みを行わない。
- **EC-224**: API の認証・権限・通信エラーを「存在しない」と解釈しない。
- **EC-225**: 不完全なドラフトを自動削除・上書きせず、保守者が修復または削除した後に再実行する。
- **EC-226**: タグ作成が競合すれば参照先を再確認し、別コミットのタグを使わない。
- **EC-227**: 必須のビルド・通常テスト・静的検査・ZIP 検証の失敗後は公開先の更新やタグ・ドラフト作成へ進まない。
  - 性能テストの失敗は FR-311（overview.md）の変更で定める明示的な例外として記録する。
- **EC-228**: 同期の検証後に公開用 main が変われば更新を中止し、強制更新しない。
- **EC-229**: 古い同期の再実行で、公開済みの新しいソースを巻き戻さない。
- **EC-230**: 同期時に開発用 master が先へ進んでも、選んだコミットの公開候補へ後続変更を混ぜない。
- **EC-231**: 同期は成功し配布だけが失敗したら、同期コミットを増やさず公開用の元の実行から復旧する。

- **EC-232**: 確認用候補とマージ結果が異なれば、固定したマージ済み SHA の候補を生成し、ローカル再確認を待つ。
  - これは通常の master 追従不要の運用で起こり得る分岐とし、同期の成功や公開済みとは扱わない。
- **EC-233**: 確認用成果物がない・期限切れ・別 PR / 別対象 SHA のものなら、公開に利用せず固定 SHA で再生成する。
- **EC-234**: 初回の公開用 main に source trailer がなければ、保守者が現状と一致する初期 base を明示するまで同期しない。
- **EC-235**: 通常 push や別リリースによって、待機中のリリースを共通の concurrency group から取り消さない。

## Requirements *(mandatory)*

### Functional Requirements

#### 変更

- **FR-169（変更）**: 保守者は開発用のリリース PR を起点に、GitHub 内でソース公開と配布ドラフト作成を行える。
  - 通常操作でローカル publish、公開用への手動コミット・push を必要としない。
  - Actions 全体の障害時のローカル配布手順は復旧用として維持する。
- **FR-173（変更）**: 公開用 Release は対象の公開コミットを指すタグに対するドラフトとして作成する。
  - ZIP・チェックサム・指定ノートを含め、Actions はコミット済みノートを使う。
  - タグがなければ検証後に作成し、公開は保守者が確認後に行う。
- **FR-179（変更）**: 公開用コマンドと開発用の現行設定・検査・テスト・手順は、GitHub 上の公開方式と整合する。
  - 既存の公開用コマンドとローカル配布 CLI を維持し、ローカル publish を通常手順から外す。
- **FR-311（変更）**: 公開候補の CI は build、Core / App の通常テスト、性能テスト、通信 API の検査を順に実行する。
  - 性能テストは他のテストと同時に実行しない。
  - build・通常テスト・通信 API 検査や公開候補の必須検証に失敗した時点で非ゼロ終了し、
    以降の検査・成果物確定・同期・ステージングを行わない。
  - 性能テストの失敗は共有ランナー上の測定のぶれを考慮した例外とし、
    その結果とログを候補に記録して後続の必須検査へ進める。
  - 同期では対象と公開ツリーが一致する候補 CI の検証結果を再利用し、macOS の build とテストを重複実行しない。
- **FR-312（変更）**: 公開手順は検査の対象・順序、性能テストの例外、候補 CI の検証結果を再利用してから公開先を更新することを明記する。

#### 追加

- **FR-322**: 公開用の配布 workflow は default branch への push と手動実行に対応し、イベント SHA に対象を固定する。
- **FR-323**: 公開用への push では配布要求が追加・更新された場合だけ配布ビルドを行う。
  - 要求なし・同一なら既存 Release を維持し、手動実行は有効な要求で配布を再試行できる。
- **FR-324**: 配布要求は `X.Y.Z` の version、数字の build 番号、空でないコミット済みノートを指定する。
  - version の各数値と build 番号は、0 単独を除き先頭の 0 を許さない。値を自動正規化しない。
  - タグを `vX.Y.Z` とし、対象コミットを変える配布には未使用のバージョンを使う。
- **FR-325**: 配布は通常テストと公開済みコミットからの隔離ビルドを通す。
  - FR-170〜172・175（overview.md）の macOS 15 以降・arm64・ad hoc 署名・ZIP とチェックサムの条件を維持する。
  - ZIP 展開後も両バージョン・署名・アーキテクチャ・日英リソースを確認する。
- **FR-326**: タグは対象コミットに一致する場合だけ再利用し、別コミットの同名タグがあれば停止する。
  - 軽量・注釈付きタグの両方を解決し、未作成なら検証後に作る。
- **FR-327**: 同名のドラフト・公開済み Release は自動更新せず停止し、再実行と復旧の手順を示す。
- **FR-328**: 公開先への書き込みは対象 repo の default branch の信頼された実行に限定する。
  - PR と fork の検査に公開先の書き込み資格情報を渡さない。
- **FR-329**: 公開用 workflow は TAK-40 の管理元を使い、公開ファイルだけで動作する。
- **FR-330**: 要求判定、除外、API 障害、タグ・Release・同期競合、無差分・古い実行・再実行を自動検証する。
- **FR-331**: 実行結果から開発用 SHA・公開用 SHA・タグ・両バージョン・チェックサム・実行 URL と判定理由を確認できる。
- **FR-332**: 開発用の同期判定は release.json 変更 PR が master にマージされたときに開始する。
  - 通常の master 更新では公開先へ書き込まず、待機中のリリースも取り消さない。PR 検証も書き込まない。
  - 候補とマージ結果が異なる場合は候補を作り直して確認待ちとし、再確認後の手動再開を提供する。
- **FR-333**: 同期対象はマージ済みリリース PR の単一コミットに固定し、後続変更を混ぜない。
  - 手動の候補生成と同期は対象の完全な source SHA を必須入力とし、
    そのコミットが master に含まれるリリース PR のマージ結果であることを確認する。
  - 起動する workflow の ref が default branch でも、対象を起動時の HEAD に読み替えない。
- **FR-334**: 同期候補は既存の公開除外・README 調整・workflow 配置と混入検査を引き継ぐ。
- **FR-335**: 公開用の更新は既存 main の先へ1コミットを追加し、開発用履歴を取り込まず強制更新しない。
- **FR-336**: 無差分の同期はコミットを作らず、古い同期で新しい公開内容を巻き戻さない。
  - 初回だけ source trailer のない公開先に対し、保守者が bootstrap_public_base を明示して一致を確認する。
  - 初回の source 対応付けに限り、tree が同じでも1つの初期化コミットを作る。以後は無差分で省略する。
  - 入力なし・不一致なら停止し、初期化を古い候補の拒否や候補の検証を省く一般的な例外にしない。
- **FR-337**: リポジトリ間同期の資格情報は公開先に限定し、検証成功後の書き込み処理にだけ渡す。
- **FR-338**: 書き込む公開ツリーが、検証に成功した対象コミットの公開候補と一致することを確認する。
- **FR-339**: 運用文書はリリース PR、同期と配布の状態、初回設定、再実行、ローカル復旧の位置づけを説明する。

- **FR-340**: リリース PR の CI は公開候補と同じファイル構成から arm64 の確認用アプリ ZIP を作る。
  - 保守者が ZIP・SHA256SUMS・出自情報を Actions からダウンロードできるようにする。
- **FR-341**: 確認用成果物には PR、PR head、ビルドしたコミット、公開ツリーの識別子、両バージョン、実行元を記録する。
- **FR-342**: 同期前に、対象 PR の成功した確認用候補とマージ済み対象コミットの公開ツリーの一致を確認する。
  - PR 候補を使う場合は最新 head と merged PR の関係も確認する。
  - ツリー不一致ならマージ済み対象 SHA の新候補を生成し、確認待ちとする。
  - 再開時は source SHA と候補 run を照合し、必須検証の成功を確認する。
- **FR-343**: 保守者は CI の最新候補をローカル PC で確認してからリリース PR をマージする。
  - PR 候補がマージ結果とも一致する場合は、マージを確認後に先へ進む操作とする。
  - 一致しない場合は固定したマージ済み SHA の新候補を再確認し、その SHA と run を指定した手動起動で同期を再開する。

### Key Entities

- **ReleaseRequest**: version / build_number / notes_file を持つコミット済み release.json。
- **PublicCandidate**: 開発用 SHA と公開ツリー・照合情報を持つ検証候補。
- **PublicCommit**: 公開用 main を親にして確定した単一コミット。
- **CandidateArtifact**: PR と CI 実行に結び付いた確認用 ZIP・チェックサム・公開ツリーと出自の記録。
- **ReleaseState**: タグ・Release の有無と参照コミット、ドラフトか公開済みか。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-170**: release.json 変更 PR のマージから、ローカル公開作業なしで配布ドラフトを1つ作れる。
- **SC-171**: 通常の master 更新・PR・fork からの公開用書き込みが0件である。
- **SC-172**: 既存 Release・別コミットのタグ・API 障害の検証で誤更新が0件である。
- **SC-173**: 同じコミットのタグだけが残った状態からタグを動かさずドラフトを作れる。
- **SC-174**: 保守者が手順を使い、取得した ZIP の日英 GUI・3ペインを確認して公開できる。
- **SC-175**: 同期候補の必須検証失敗時、公開用 main が更新されない。
- **SC-176**: 同じ候補の同期再実行で、追加の公開コミットが0件である。
- **SC-177**: 古い候補・公開先競合の検証で、新しい公開内容の巻き戻しが0件である。

- **SC-178**: 保守者がリリース PR の CI 成果物を取得し、ローカルでビルドせずアプリの GUI を確認できる。
- **SC-179**: 確認用候補が欠落・別対象・公開ツリー不一致の場合、新候補の再確認と再開操作まで公開用への同期が0件である。

## Assumptions

- **A-96（変更）**: 保守者がリリース PR の作成・レビュー・マージと、GUI・ドラフト確認後の公開を行う。
  - 公開用への同期コミット・push と通常のタグ作成は Actions が行う。
  - Actions 全体の障害時だけ、担当者がローカル復旧を行う。
- **A-199**: 開発用と公開用の2リポジトリを維持する。
- **A-200**: リリース時期と version / build / notes は保守者が release.json 変更 PR で決定する。
- **A-201**: Developer ID 署名・公証、Intel / Universal、自動更新、最終公開の自動化は今回の範囲外とする。
