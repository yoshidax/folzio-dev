## 既存の仕様との関係

この feature は、製品仕様（`specs/product/`）を書くための開発用の検査と、書き方のルールを扱う。アプリの動作は変えない。

- TAK-61 で `specs/product/` を1行1事項の箇条書きへ整理した。この feature は、その形を保つための検出と文書化を行う
- ID の重複の検査（`scripts/dev/check-spec-ids.sh`。`docs_private/cloud-agent-workflow.md` の 7 章）は変えない
- 検証ゲート・CI・テンプレートへの組み込みは TAK-63 で扱う。この feature では、検査を単独で実行できるようにするまでとする
- 「1文=1行」の採用の判断と既存文書の再整形は TAK-64 で扱う。この feature の検出項目は、どちらの方針でも使えるものに絞る

## Clarifications

### Session 2026-11-04

- Q: 現在の `specs/product/` にある、引用と英語句の行をまたぐ分断（8 か所）をどう扱うか？ → A: エラーとし、この feature で
  形式のみの修正（改行の位置の変更）を行う（`overview.md` を除く 7 か所）。修正が形式のみであることは、この feature の equivalence チェックで確かめる。
  `overview.md` の「出発点となった要望」の引用は、長い利用者の入力をそのまま引いたものなので、検出器の設定で対象外にする。
  （ほかの案: 警告にとどめて件数を基準値に記録し、修正を TAK-64 に回す案は、検出の目的である再発の防止が、既存の崩れを残したままでは
  弱くなるため採らない）
- Q: この feature の要件を `specs/product/` のどこに反映するか？ → A: TAK-40 の前例に合わせ、`overview.md` に新しい節
  「製品仕様の形式の検査」を作り、FR-296 以降を置く。書き方のルールそのものは `specs/product/README.md` に置く。
- Q: equivalence チェックの合否の基準は？ → A: 文字列の移動（表のセルから「表の詳細」への移動など）と、既知の形式の印
  （`下記`、「表の詳細」、詳細の見出し）だけなら成功とする。それ以外の追加・削除があれば失敗とする。どちらの場合も、
  追加・削除・移動の一覧を、人間がレビューする候補として出す。

## User Scenarios & Testing *(mandatory)*

### User Story 64 - 製品仕様の形式の崩れを検出する (Priority: P1)

保守者と Agent は、`specs/product/` に追記・変更した後に形式の検査を実行し、崩れた箇所をファイルと行の番号で知る。
エラーがあれば検査は失敗する。警告は表示するが、件数が記録した基準値を超えたときだけ失敗する。

**Why this priority**: TAK-62 の直接の目的。Living spec に追記を続けると、TAK-61 のレビューで指摘された崩れ
（引用名やインラインコードの分断、表の行の崩れ、長い行）が再発する。人間のレビューだけでは見落とす。

**Independent Test**: 検出項目ごとにわざと崩した文書を用意して検査を実行し、それぞれが該当する行とともに報告され、
エラーなら失敗することを確かめる。崩していない文書では成功することを確かめる。

**Acceptance Scenarios**:

1. **US64-AS1**: **Given** この feature の修正後の `specs/product/`、**When** 形式の検査を実行する、**Then** エラーは 0 件で、
   警告の件数は記録した基準値以下であり、検査は成功する。
2. **US64-AS2**: **Given** インラインコード、引用名、英語句のどれかを途中で改行した行がある、**When** 形式の検査を実行する、
   **Then** その行がエラーとして報告され、検査は失敗する。
3. **US64-AS3**: **Given** 物理的に2行へまたがる表の行、列数が揃わない表、本体の行がない表のどれかがある、
   **When** 形式の検査を実行する、**Then** その表がエラーとして報告され、検査は失敗する。
4. **US64-AS4**: **Given** 表のセルが `下記` なのに、表の直後の「表の詳細」に対応する項目がない、**When** 形式の検査を実行する、
   **Then** その行がエラーとして報告され、検査は失敗する。
5. **US64-AS5**: **Given** 表示幅が 120 桁を超え 160 桁以下の行を1行追加した、**When** 形式の検査を実行する、
   **Then** その行が警告として報告され、警告の件数が基準値を超えるので検査は失敗する。
6. **US64-AS6**: **Given** 警告の件数が基準値を下回った、**When** 形式の検査を実行する、**Then** 検査は成功し、
   基準値を更新できることが表示される。
7. **US64-AS7**: **Given** 対訳表の長いセル、または設定で対象外にした引用がある、**When** 形式の検査を実行する、
   **Then** それらは幅や分断の検出の対象にならない。

### User Story 65 - 形式のみの変更であることを確かめる (Priority: P1)

保守者と Agent は、`specs/product/` の改行の位置や構造だけを変える PR（形式のみの PR）で、比較の基準とする版を指定して
equivalence チェックを実行する。本文の文字列が変わっていないかを合否で知り、追加・削除・移動された文字列を一覧で確かめる。

**Why this priority**: TAK-61 のような整形では、意味を変えないことが前提だが、人間が数千行の差分を読んで確かめるのは難しい。
係り受けの変化のように機械で判定できないものは残るが、文字列の追加・削除と移動を一覧にすれば、レビューの対象を絞れる。

**Independent Test**: 一時的なリポジトリで、基準の版に対して改行の位置だけを変えた場合、表のセルを「表の詳細」へ移した場合、
語句を1つ書き換えた場合をそれぞれ作り、合否と一覧の内容を確かめる。

**Acceptance Scenarios**:

1. **US65-AS1**: **Given** 基準の版から、改行の位置・インデント・箇条書きの入れ子だけを変えた、**When** equivalence チェックを
   実行する、**Then** 成功し、差分がないことが表示される。
2. **US65-AS2**: **Given** 表のセルの文を「表の詳細」へ移し、セルを `下記` にした、**When** equivalence チェックを実行する、
   **Then** 成功し、移動した文字列が移動元と移動先の位置とともに一覧に出る。
3. **US65-AS3**: **Given** 語句を1つ書き換えた、文を1つ追加した、または文を1つ削除した、**When** equivalence チェックを実行する、
   **Then** 失敗し、追加・削除された文字列が位置とともに一覧に出る。
4. **US65-AS4**: **Given** 作業ツリーにコミットしていない変更がある、**When** equivalence チェックを実行する、**Then** その変更も
   比較の対象になる。

### User Story 66 - 書き方のルールを文書で確かめる (Priority: P2)

保守者と Agent は、`specs/product/README.md` と `AGENTS.md` を読んで、製品仕様の書き方のルールと、検査の実行方法、
警告とエラーの扱い、対象外の指定のしかたを確かめられる。

**Why this priority**: 検出器だけでは、なぜその形にするのかが伝わらない。書く前にルールが分かれば、崩れを作らずに済む。

**Independent Test**: 文書だけを読んで、表のセルが長くなったときの書き方、検査の実行方法、警告の基準値の更新のしかた、
対象外にする方法を答えられるかを確かめる。

**Acceptance Scenarios**:

1. **US66-AS1**: **Given** `specs/product/README.md`、**When** 保守者が要件を追記しようとする、**Then** 箇条書き・表・改行の
   書き方のルールと、検査の実行方法が分かる。
2. **US66-AS2**: **Given** `AGENTS.md`、**When** Agent が `specs/product/` を変更しようとする、**Then** 書き方のルールの要点と、
   詳細が `specs/product/README.md` にあることが分かる。

### Edge Cases

- **EC-207**: コードブロックの中の行は、幅・引用・インラインコードの検出の対象にしない。コードブロックの中の `|` で始まる行も表として扱わない。
- **EC-208**: 1行の中で閉じている引用（「」・“ ”）とインラインコードは、行の長さによらず分断として扱わない。
  入れ子の引用（「」の中の「」）は、開きと閉じの数で判定する。
- **EC-209**: 表のセルの中の `\|`（エスケープした区切り）は、列の区切りとして数えない。
- **EC-210**: 同じキーの行が表に複数ある場合（例: `contracts/settings.md` の「ファイル操作」）、`下記` の行は、
  「表の詳細」の項目の見出しがその行のキーで始まるものと対応づける。
- **EC-211**: equivalence チェックで、基準の版にないファイルが増えた、または基準の版のファイルがなくなった場合は、
  そのファイルの本文全体を追加または削除として扱う。ほかのファイルとの間の移動は、移動として扱う。
- **EC-212**: 基準の版として、存在しないコミットや作業ブランチと共通の祖先がないコミットを指定した場合、equivalence チェックは
  比較をせずに、理由を示して失敗する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-296**: 形式の検査（`scripts/dev/check-spec-format.py`）は、既定で `specs/product/` 以下のすべての Markdown ファイルを調べ、
  見つけた崩れを、ファイル・行の番号・検出項目・重大度（エラーまたは警告）とともに表示しなければならない。
  検査は Python の標準ライブラリだけを使い、Cloud と保守者のローカルの両方で動かなければならない。
- **FR-297**: 形式の検査は、次をエラーとして検出しなければならない。
  - コードブロックと表以外の行で、表示幅が 160 桁を超えるもの
  - 表の行が物理的に複数行にまたがるもの（`|` で始まり `|` で終わらない行と、表の直後の `|` で終わる行）
  - 列数が揃わない表、区切りの行がない表、本体の行がない表
  - インラインコード、引用（「」・“ ”）が行をまたぐもの
  - 英語句が行をまたぐもの（行末が英字で、続きの行が英小文字で始まる）
  - `下記` のセルに対応する項目が、表の直後の「表の詳細」にないもの
- **FR-298**: 形式の検査は、次を警告として検出しなければならない。
  - コードブロックと表以外の行で、表示幅が 120 桁を超えるもの
  - 対訳表以外の表で、表示幅が 80 桁を超えるセル
  - FR・SC・EC・A・USn-ASm の定義の本文（子項目を除く）が2つ以上の文を含むもの
- **FR-299**: 表示幅は、文字の East Asian Width が W（全角）または F（全角英数）なら 2 桁、それ以外（A（曖昧）を含む）は 1 桁として
  数えなければならない。行頭のインデントも幅に含める。
- **FR-300**: 形式の検査は、エラーが1件でもあれば失敗しなければならない。警告は、ファイルと検出項目ごとの件数を基準値として
  記録したファイルと比べ、どれかが基準値を超えたときだけ失敗しなければならない。基準値を下回ったときは成功とし、
  基準値を更新できることを示す。基準値は、検査のオプションで現在の件数に更新できなければならない。
- **FR-301**: 幅と分断の検出の対象外にするファイル・表・範囲は、検出器の設定ファイルで明示しなければならない。
  対訳表（`contracts/localization.md` の、日本語と英語の列を持つ表）のセルは、セルの幅の検出の対象外とする。
  `overview.md` の「出発点となった要望」の引用は、引用の分断の検出の対象外とする。
- **FR-302**: equivalence チェック（`scripts/dev/check-spec-equivalence.py <base>`）は、指定した版と作業ブランチの共通の祖先にある
  `specs/product/` と、作業ツリーの `specs/product/`（コミットしていない変更と追跡していないファイルを含む）を比べなければならない。
- **FR-303**: equivalence チェックは、空白・改行・インデント、箇条書きと見出しの記号、強調の記号、表の区切りの記号と区切りの行、
  句読点（`。`・`、`・`,`）の違いを無視して、ファイルごとに本文の文字列を比べなければならない。
  既知の形式の印（`下記` のセル、「表の詳細」の行、「表の詳細」の各項目の見出し）は、比べる前に取り除く。
- **FR-304**: equivalence チェックは、比べて異なった文字列を「移動」（削除された文字列が、同じまたは別のファイルの追加された文字列に
  含まれる）、「追加」、「削除」に分け、それぞれ基準の版と作業ツリーのファイルと行の番号とともに一覧で表示しなければならない。
  「追加」と「削除」がなければ成功し、1件でもあれば失敗しなければならない。
- **FR-305**: 形式の検査と equivalence チェックには、検出項目と合否の判定ごとに、わざと崩した入力で失敗することと、
  崩していない入力で成功することを確かめる回帰テストがなければならない。
- **FR-306**: `specs/product/README.md` は、製品仕様の書き方のルール（1つの箇条書きに1つの要件・条件・例外、条件と例外は子項目、
  表のセルは短い要約にして詳細は「表の詳細」に置く、`下記` と「表の詳細」の対応づけ、インラインコード・引用・英語句・表の行を
  途中で改行しない）と、検査の実行方法、警告と基準値、表示幅の数え方、対象外の指定のしかたを示さなければならない。
  `AGENTS.md` は、書き方のルールの要点と、詳細の参照先を示さなければならない。

### Key Entities

- **形式の検査**: `specs/product/` の Markdown を読み、崩れをエラーと警告として報告する検出器（`scripts/dev/check-spec-format.py`）
- **基準値**: 警告の件数を、ファイルと検出項目ごとに記録したファイル。形式の検査が、警告の増加を判定するのに使う
- **検出器の設定**: 幅と分断の検出の対象外にするファイル・表・範囲と、しきい値を明示したファイル
- **equivalence チェック**: 基準の版と作業ツリーの `specs/product/` の本文を比べ、移動・追加・削除の一覧と合否を出す検査
  （`scripts/dev/check-spec-equivalence.py`）
- **形式の印**: 整形で加わる、本文ではない文字列（`下記` のセル、「表の詳細」の行、「表の詳細」の各項目の見出し）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-157**: この feature の修正後の `specs/product/` で、形式の検査のエラーが 0 件である。警告の件数は、基準値として記録されている。
- **SC-158**: FR-297 と FR-298 の検出項目のそれぞれについて、わざと崩した入力が 100% 検出される（回帰テストで確かめる）。
- **SC-159**: 改行の位置だけを変えた変更と、表のセルから「表の詳細」への移動だけの変更で、equivalence チェックが成功する。
  語句を1つでも追加・削除・書き換えた変更では、equivalence チェックが失敗し、その文字列が一覧に出る。
- **SC-160**: この feature で行う既存の分断の修正（7 か所）が、equivalence チェックで差分なしと判定される。
- **SC-161**: 保守者と Agent が、`specs/product/README.md` と `AGENTS.md` だけを読んで、書き方のルールと検査の実行方法を答えられる。

## Assumptions

- **A-187**: 検査を検証ゲート・CI・PR のテンプレートへ組み込むのは TAK-63 で行う。この feature の時点では、検査は手で実行する。
- **A-188**: 「1文=1行」を採るかどうかは TAK-64 で決める。採った場合は、行の幅のしきい値と警告の基準値を TAK-64 で見直す。
- **A-189**: 子項目への分割による係り受けの変化と、移動による文脈の変化は、機械では判定できない。equivalence チェックの一覧を、
  人間がレビューする前提とする。
- **A-190**: 対象は `specs/product/` だけとする。feature ディレクトリ（`specs/NNN-xxx/`、`specs/TAK-<nn>-<slug>/`）の文書は、
  凍結した記録なので検査しない。
- **A-191**: 保守者のローカルの Python は、macOS の Command Line Tools の Python 3.9 の場合がある。検査とテストは Python 3.9 で動く書き方にする。
