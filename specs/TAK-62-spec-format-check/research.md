計測と試作は 2026-11-04 に `origin/master` の `f734a08` で行った（spec.md の「現状」）。

## R1 実装の言語と実行環境

- **Decision**: 2つの検査を Python 3 の標準ライブラリだけで書く（`scripts/dev/check-spec-format.py`、
  `scripts/dev/check-spec-equivalence.py`）。Python 3.9 で動く書き方にする（`match` 文、`X | Y` の型注釈、`tomllib` を使わない）
- **Rationale**: Issue の方針（外部パッケージに依存しない、Cloud でも動く）。表示幅の計算（`unicodedata`）と差分（`difflib`）が
  標準ライブラリにある。保守者のローカルの `python3` は、macOS の Command Line Tools の 3.9 の場合がある（A-191）。
  Cloud は 3.13
- **Alternatives considered**: Issue の仮の名前の `check-spec-equivalence.sh` は、git の操作だけをシェルで書き、比較を Python に
  渡す形になり、2つのファイルに分かれる。比較の本体が Python なので、1つの `.py` にまとめる。既存の `check-spec-ids.sh` は変えない

## R2 Markdown の読み方

- **Decision**: 行単位の状態機械で読む。コードブロック（行頭の空白の後の ` ``` `）の中と外、表（行頭の空白の後が `|` の行が続くまとまり）、
  見出し（`#`）、箇条書きの項目（`- `、`* `、`1. `）、続きの行（それ以外の空行でない行）を区別する
- **Rationale**: `specs/product/` は GitHub Flavored Markdown のごく一部（見出し・箇条書き・表・コードブロック・強調・インラインコード・
  リンク）しか使っていない。行の種類が分かれば、全検出項目を判定できる。Markdown のパーサーは標準ライブラリにない
- **Alternatives considered**: 表を Markdown の仕様どおりに解釈する（表は区切りの行の直後から、`|` を含む行が続く限り続く）と、
  崩れた行（`|` で終わらない行）が表の一部として吸収され、検出できない。TAK-61 では、行単位の単純なパーサーが崩れた表を分割して壊した
  （Issue の Agent notes）。検出器は、`|` で始まる行のまとまりを表とし、まとまりの直後の `|` で終わる行を崩れとして報告する

## R3 表示幅

- **Decision**: `unicodedata.east_asian_width` が `W` または `F` の文字を 2 桁、それ以外（`A`・`H`・`Na`・`N`）を 1 桁とする。
  行頭のインデントも含め、行末の空白は除く。結合文字の幅は 0 にしない（`specs/product/` に結合文字はない）
- **Rationale**: エディタと GitHub の等幅の表示で、日本語の文字は 2 桁、記号の多くは 1 桁で表示される。
  `A`（曖昧）は `→`・`○`・`×` などで、欧米のフォントでは 1 桁になるため 1 桁とする（Issue の仮の案のとおり）
- **Alternatives considered**: 文字数で数える案は、日本語の行と英語の行で見た目の長さが倍違うため採らない

## R4 エラーと警告、基準値

- **Decision**: エラーは1件でもあれば失敗。警告は、基準値ファイル（`scripts/dev/spec-format-baseline.json`）に、
  `specs/product/` からの相対パスごと・検出項目ごとの件数を記録し、どれかが基準値を超えたら失敗する。基準値を下回ったら成功とし、
  `--update-baseline` で更新できることを表示する。`--update-baseline` は、エラーが 0 件のときだけ基準値を書き換える
- **Rationale**: 総数だけを比べると、あるファイルで直して別のファイルで崩した場合に見逃す。ファイルと項目ごとに比べれば、
  増えた場所を示せる。基準値の更新を明示的なオプションにすると、差分として PR に現れ、レビューできる
- **Alternatives considered**: 行の番号まで記録する案は、行の追加で番号がずれるたびに基準値が壊れるため採らない

## R5 しきい値と現状の件数

| 検出項目 | 重大度 | しきい値 | 現状 |
|---|---|---|---|
| 行の幅 | 警告 | 120 桁を超える | 10 |
| 行の幅 | エラー | 160 桁を超える | 0 |
| セルの幅（対訳表を除く） | 警告 | 80 桁を超える | 41 |
| 複数の文を含む定義 | 警告 | 2 文以上 | 34 |

- **Decision**: 上のしきい値を設定ファイルに置く。セルの幅は 80 桁（日本語で 40 文字）とする
- **Rationale**: 現状で 160 桁を超える行は 0 件で、エラーにしても既存の文書が通る。セルの幅は、60 桁で 86 件、80 桁で 41 件、
  100 桁で 21 件、120 桁で 5 件だった。「表のセルは短い要約」の目安として 80 桁を採り、既存の超過は基準値に入れる
- **Alternatives considered**: セルの幅をエラーにする案は、既存の 41 件を直す必要があり、形式の整理（TAK-64）の範囲になるため採らない

## R6 引用とインラインコードの分断

- **Decision**: コードブロックと表以外の各行で、インラインコードを除いた後に `「` と `」`、`“` と `”` の数を数え、1行の中で
  閉じていなければ分断のエラーとする。インラインコードは、行の中のバッククォートの数が奇数ならエラーとする（同じ数のバッククォートで
  閉じるという Markdown の規則に従い、連続したバッククォートの並びを1つの区切りとして数える）
- **Rationale**: 1行の中で閉じていれば、改行による分断はない（EC-208）。インラインコードの中の `「` は引用ではないので除く
- **Alternatives considered**: 段落全体で対応を調べる案は、行をまたいで対応していても「分断」なので、検出の目的に合わない

## R7 英語句の分断

- **Decision**: 続きの行（箇条書きの項目・見出し・表・コードブロック・空行でない行）について、前の行の末尾が英字で、
  その行が英小文字で始まるとき、英語句の分断のエラーとする
- **Rationale**: 現状の該当は 3 件で、すべて実際の分断（`window-layout.md` の `Confirm before / copying`、`regardless / of this setting`）
  だった。行頭が英小文字の行だけを調べる案（Issue の候補）は 19 件で、`zip の…` のように日本語の文中の英単語で始まる正常な行を多く含んだ
- **Alternatives considered**: 対訳表の語句を辞書にする案（Issue の候補）は、対訳表にない英語句（メニュー名以外の説明文）を見逃す

## R8 `下記` と「表の詳細」の対応づけ

- **Decision**: 表の本体の行で、いずれかのセルが `下記` だけのものを対象にする。行のキーは最初の列のセル（強調の `**` を除く）とする。
  表の直後（空行を挟んでよい）の行が `**表の詳細**` で、それに続く最上位の箇条書きの項目のうち、見出し（行頭の `**…**`）が
  キーで始まるものが1つ以上あれば対応しているとする。項目の列は、見出しの後の `（列名）` で示す
- **Rationale**: 現状の 24 行は、すべてこの規則で対応した。`contracts/keyboard-and-menus.md` の `⌃⌘2` は、見出しが
  `⌃⌘2 / 表示 > ファイルリストのみ表示 / …` と長い。`contracts/settings.md` の「ファイル操作」は同じキーの行が複数あり、見出しは
  `ファイル操作 / 補足説明` である（EC-210）。完全一致では、この 2 か所が対応しない
- **Alternatives considered**: 「表の詳細」に `下記` の行と同じ数の項目があるかで判定する案は、同じキーの複数の行を1つの項目で
  説明する場合に誤る

## R9 複数の文を含む定義

- **Decision**: 定義（`- **FR-xxx**:` などで始まる項目）の本文を、子項目の前までの続きの行を含めて連結し、`。` で区切った空でない
  部分が 2 つ以上なら警告とする
- **Rationale**: 1つの項目に1つの要件という方針を、機械で確かめられる範囲で表す。条件・例外を子項目へ分ければ 1 文になる。
  現状は 34 件で、すべて警告として基準値に入れる

## R10 対象外の指定

- **Decision**: 設定ファイル（`scripts/dev/spec-format-config.json`）の `exclusions` に、`file`（`specs/product/` からの相対パス）、
  範囲（`section`: 見出しの文字列。その見出しから、同じかより上位の次の見出しまで。または `table_columns`: 見出しの行が含む列名）、
  対象外にする検出項目（`rules`）、理由（`reason`）を書く。最初の設定は次の 2 件
  - `overview.md` の `## 出発点となった要望`: `quote-split`、`english-split`、`line-width`（利用者の入力をそのまま引いた長い引用）
  - `contracts/localization.md` の、`日本語` と `英語` の列を持つ表: `cell-width`（対訳の対応を壊さないため、行を分けない）
- **Rationale**: Issue の方針（対象外にするファイル・表は検出器の設定で明示する）。範囲を見出しや列名で指定すると、行の追加で
  ずれない
- **Alternatives considered**: 文書の中にコメント（`<!-- spec-format: ignore -->`）で書く案は、`specs/product/` の本文に検査のための
  記述が混ざり、equivalence チェックの比較にも影響するため採らない

## R11 equivalence チェックの比較

- **Decision**:
  1. 基準の版は `git merge-base <base> HEAD` とし、その版の `specs/product/` の `.md` を `git ls-tree` と `git show` で読む。
     作業ツリーは、ファイルシステムの `specs/product/` の `.md` を読む（コミットしていない変更と追跡していないファイルを含む）
  2. 各ファイルを正規化する。コードブロックの区切りの行、表の区切りの行、`**表の詳細**` の行を除き、行頭の空白・箇条書きと見出しの記号を除き、
     「表の詳細」の最上位の項目の見出し（`**…**` と続く `（…）`・`:`）を除き、`下記` だけのセルを除く。続けて、すべての行を連結し、
     NFC に正規化して、空白・`|`・`*`・`。`・`、`・`,` を除く。正規化後の各文字に、元のファイルの行の番号を対応づける
  3. 正規化後の文字列が同じファイルは一致とする。異なるファイルは `difflib.SequenceMatcher`（`autojunk=False`）で文字単位に比べ、
     削除された断片と追加された断片を集める（基準の版にないファイルは全体が追加、作業ツリーにないファイルは全体が削除。EC-211）
  4. 削除された断片を長い順に、全ファイルの追加された断片の中から探し、見つかればその部分を「移動」として消し込む。
     残った削除の断片は「削除」、残った追加の断片は「追加」とする
  5. 「移動」「追加」「削除」を、基準の版と作業ツリーのファイルと行の番号、断片の先頭（最大 80 文字）とともに表示する。
     「追加」と「削除」がなければ終了コード 0、あれば 1、引数や git の誤りは 2 とする
- **Rationale**: TAK-61 の差分で試すと、文単位・項目単位で比べる案は、子項目への分割で文の区切りが変わるだけで、15 ファイルで
  455 件の削除と 1325 件の追加が出て、レビューの役に立たなかった。文字単位で記号を除いて比べる案は、11 ファイルが一致し、
  残りは表から「表の詳細」への移動と、形式の印の追加だけだった。形式の印を先に除けば、移動だけが残る。
  1ファイルの比較は最大 4 秒（`contracts/keyboard-and-menus.md`、全体が整形された場合）で、全体でも 15 秒以内に終わる
- **Alternatives considered**: 空白を除いた全文の一致だけを見る案は、合否は出せるが、どこが変わったかと、移動かどうかを示せない。
  Issue の「単純な空白除去の比較では、文の順序の入れ替えや表の行の追加を見逃す」は、一致の判定ではなく、行の集合として比べる場合の
  指摘と解釈した。文字単位の比較では、順序の入れ替えは「移動」、表の行の追加は「追加」として一覧に出る

### T009 TAK-61 の差分での試行

`f734a08` をチェックアウトした一時的な clone で、`b4e48eb` を基準に比べた。R11 の方式から、次の 3 点を改めた。

1. 文字単位の差分では、移動した断片の境界が、隣の同じ文字（`）`、`る` など）と対応づけられて 1〜2 文字ずれ、
   「追加」と「削除」の組として残った。移動の判定で、断片全体が見つからないときは、追加された断片との最長の共通部分
   （4 文字以上）を移動とし、残りの部分をもう一度判定するようにした
2. 「表の詳細」の見出しを丸ごと取り除くと、表の行そのものを詳細へ移した場合（`contracts/keyboard-and-menus.md` の
   「拡大・縮小のボタングループ」など）に、見出しにしか残っていない行のキーが「削除」になった。また、見出しは `下記` の行に
   限らず、表のどの行のキーも参照していた。見出しから取り除くのは、直前の表の行のキーと重なる先頭の部分だけにした
3. 見出しの直後の括弧（`（動作）`、`（FR-046）`）は、列名またはその行のセルの値と同じなら取り除き、それ以外は括弧だけを
   取り除いて中身を比べるようにした。表の外へ出した行の値を、見出しで括弧に包むことがあるため

結果は、移動 69 件、追加 2 件、削除 0 件で、終了コードは 1 だった。追加の 2 件は、TAK-61 で実際に本文が変わった箇所である。

- `contracts/settings.md`: 詳細の見出しに「/ 補足説明」を書き足した
- `file-list.md`: 番号付きの項目「5. Finder に表示」を、前の行の文中へ結合し、「5.」が本文になった

この変更で、spec.md の FR-303 と data-model.md の「形式の印」の「「表の詳細」の各項目の見出し」は、正確には
「見出しのうち直前の表の行のキーと重なる部分、見出しの直後の括弧（列名・セルの値と同じ中身は括弧ごと）」になる。
`specs/product/` へ反映するときは、この正確な表現で書く。
