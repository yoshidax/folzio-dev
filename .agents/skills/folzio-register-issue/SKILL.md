# Folzio の Issue を登録する

ユーザーの依頼を新規 Issue の提案、または指定された既存 Issue の整理として扱う。内容がない場合や理解できない場合は、何を記録したいか尋ねる。既存 Issue の場合は Linear MCP で本文・属性・関連するコメントを取得し、Folzio プロジェクトの対象 Issue であることを確認する。リポジトリの `AGENTS.md` を読み、開発用の default branch（現在は `master`）を基準に、関連する `specs/product/` の文書とコードまたはテストの関連箇所を絞って確認する。現在のブランチと未コミットの変更も確認し、重要な場合は基準との差を区別する。別のブランチや未コミットの変更が依頼の対象なら、それも確認して基準との違いを明示する。参照したブランチとコミットを調査結果に示し、default branch を確認できない場合はその制約を報告する。ブランチを切り替えず `git show` などで参照し、リポジトリのファイル変更、ブランチ作成、正式な Spec Kit ワークフローの実行、修正の実装は行わない。

依頼をバグの可能性、機能追加・仕様変更、リファクタリング、その他・保守に分類し、内容に筋が通っているか、Folzio に関係するかを大まかに判断する。機能追加ではユーザーの目的と範囲を捉え、詳細要件を創作したり、製品上の決定を下したり、Spec Kit に委ねる詳細化や設計を行ったりしない。既存の動作があることだけを理由に、望まれた変更を却下しない。

バグの可能性がある場合は、報告を関連する現行仕様と確認したコードに照らし合わせる。該当する仕様 ID があれば示し、観察された症状と推測した原因を区別する。再現手順を創作せず、根拠なく再現したと主張しない。実装が仕様に反している場合はバグの可能性として扱う。仕様がない、または仕様が誤っていると思われる場合は、`AGENTS.md` に従い仕様変更の可能性として扱う。これは予備的な振り分けであり、必要な正式バグ診断や修正への承認ではない。

登録の要否、意図した動作、バグと仕様変更のどちらに当たるかに関わる重要な不明点がある場合は、登録前にユーザーに確認する。特に、バグ報告の症状、期待動作、仕様との食い違いが不明な場合に確認する。調査結果を踏まえて要点を絞って質問し、後の Spec Kit の作業で決められる詳細は求めない。未解決の報告でもユーザーが管理する価値があると確認した場合は、結論を断定せず不明点を記録する。依頼が明らかに妥当でない、または既に満たされている場合は根拠を説明し、ユーザーが残る要望を明確にしない限り登録しない。

利用可能な Linear MCP で Folzio プロジェクトを検索し、適切な場合は TAK チームも検索して、重複の可能性を調べる。ツールが対応する場合は完了済み・アーカイブ済み Issue も含め、候補を確認する。実質的に重複する可能性がある場合は候補を示して別の Issue を作るか尋ねる。明示的な依頼なしに既存 Issue を変更しない。検索やプロジェクトの特定に失敗した場合は制約を報告し、確認できるまで Issue を作成しない。

## テンプレートとラベル

Linear の TAK チームの標準 Issue テンプレートをフォーマットの正本とする。Linear MCP で一覧と内容・既定属性を取得し、分類に対応するものを使う。

| 種別 | テンプレート名 | 種別ラベル |
|---|---|---|
| バグ | Folzio - バグ | Bug |
| 機能追加・仕様変更 | Folzio - 機能追加・仕様変更 | Feature |
| リファクタリング | Folzio - リファクタリング | Refactor |
| その他・保守 | Folzio - その他・保守 | Chore |

テンプレートの見出しに沿って簡潔な日本語で記入する。不明な内容は推測で埋めず未確認とし、不要な項目は省略する。根拠のある関連仕様 ID・コードの場所、未解決の質問を必要に応じて記載する。Feature の受け入れ条件は必要に応じて大まかに記し、解決策を指定しない。テンプレートや必要なラベルを取得・特定できない場合は勝手に新設せず、状況を報告する。

新規登録の依頼が十分明確で管理対象として適切なら、ユーザーの登録依頼を Issue 1 件の作成許可として扱い、別途承認を求めない。`AGENTS.md` に記載された Folzio プロジェクトと TAK チームに、該当するテンプレートを指定して Linear MCP で作成する。取得したテンプレートに沿って作った説明と簡潔なタイトルを指定し、作成後にプロジェクトと種別ラベルを確認する。ユーザーから指定がない限り担当者や優先度を設定せず、ステータスはテンプレートの既定値を使う。実装には着手しない。

## 既存 Issue の整理

ユーザーが指定した既存 Issue の整理を依頼した場合は、その Issue のみを更新する。元の記述、ユーザーの意図、添付・リンク、既存のコメントを保持し、関連する調査結果や不明点を適切な箇所に追記する。テンプレートへの全面的な書き換えは行わず、既存の見出しを優先する。既存の分類ラベルと調査結果が食い違う、または削除・意味の変更が必要な場合は、先にユーザーに確認する。種別が明確で種別ラベルが未設定なら、対応するラベルを追加できる。他のラベル、プロジェクト、担当者、優先度、ステータスは変更しない。対象 Issue 自身を重複候補に含めない。

作成・更新後は Issue の ID、タイトル、URL、分類、変更内容と重要な不明点を報告する。作成に失敗した場合や結果が曖昧な場合は、むやみに再試行しない。まず新たに作成された一致する Issue を検索し、結果を報告するか、依然として不明な場合はユーザーに確認する。
