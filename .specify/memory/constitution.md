# my_img_viewer Constitution

## Core Principles

### I. ローカル完結・プライバシー

- 画像ファイル、そのメタデータ（EXIF・位置情報を含む）、ファイルパスを外部ネットワークへ
  送信してはならない（MUST NOT）。
- テレメトリ、利用統計、クラッシュレポートの自動送信を実装してはならない（MUST NOT）。
- アプリの全機能はオフラインで動作しなければならない（MUST）。ネットワークを必要とする機能を
  追加する場合は、spec で明示し、ユーザーの明示的な操作でのみ通信を開始し、本憲章の改定を
  経なければならない（MUST）。
- ユーザーの画像ファイルを暗黙に変更・移動・削除してはならない（MUST NOT）。破壊的操作は、
  ユーザーの明示的な指示に加えて、実行前の確認または取り消し可能性（ゴミ箱経由など）の
  いずれかを必須とする（MUST）。

**Rationale**: 画像は個人情報を多く含む。ローカル完結を前提にすることで、プライバシーと
信頼性を設計段階で保証する。取り消し可能な操作では確認を省略できる余地を残し、
整理作業の効率と安全性を両立する。

### II. 体感パフォーマンス

- UI スレッドで画像デコードやディレクトリ走査などの重い処理を行ってはならない（MUST NOT）。
  これらはバックグラウンドで実行し、操作への応答を妨げないこと。
- 以下を基準値とし、計測可能な形で検証しなければならない（MUST）:
  - 先読み済みの画像への前後切替: 100ms 以内に表示
  - 起動からファイル指定で開いた最初の画像の表示: 1 秒以内（一般的な 24MP 以下の JPEG）
  - 10,000 ファイルを含むフォルダを開いても UI がフリーズしない
- デコード済み画像のキャッシュには明示的なメモリ上限を設けなければならない（MUST）。
  上限なしのキャッシュは禁止。
- 性能に影響する変更は、基準値に対する計測結果を PR に記載しなければならない（MUST）。

**Rationale**: 画像ビューアの価値は「すぐ開き、すぐ切り替わる」ことにある。数値基準を
置くことで、性能劣化を主観ではなく計測で検出する。

### III. キーボードファースト & アクセシビリティ

- 主要操作（開く、次/前、拡大/縮小/フィット、全画面、閉じる）はすべてキーボードのみで
  実行できなければならない（MUST）。
- 新しい操作を追加する場合、キーボードショートカットまたはキーボードで到達可能な手段を
  同時に提供しなければならない（MUST）。
- UI 要素は OS 標準のアクセシビリティ API（スクリーンリーダー等）から識別可能な
  ラベルを持たなければならない（MUST）。
- OS のダークモード・視差効果を減らす等の設定を尊重すべきである（SHOULD）。

**Rationale**: 大量の画像を素早く閲覧する用途ではキーボード操作が最も効率的であり、
同時にアクセシビリティの土台にもなる。

### IV. テスト必須

- 画像の読み込み・デコード、ファイル列挙と並び順、キャッシュ、ズーム/パン計算などの
  コアロジックには自動テストを伴わなければならない（MUST）。テストを先に書くか後に書くかは
  問わない。
- バグ修正には、そのバグを再現するテストを含めなければならない（MUST）。
- 破損ファイル、非対応形式、巨大画像、権限のないファイルなど異常系入力のテストを
  含めなければならない（MUST）。アプリは異常系でクラッシュしてはならない（MUST NOT）。
- テストがすべて通らない変更をマージしてはならない（MUST NOT）。
- UI の見た目そのものの自動テストは必須としないが、コアロジックは UI から分離し、
  単体でテスト可能に保つこと（MUST）。

**Rationale**: 画像入力は多様で壊れやすい。順序は柔軟にしつつ、テストの存在と
異常系の網羅を必須にすることで品質を担保する。

### V. シンプルさ（YAGNI）

- 現在の spec が要求していない機能・設定項目・抽象化・プラグイン機構を追加してはならない
  （MUST NOT）。
- 新しい外部依存の追加は、標準ライブラリや既存依存で代替できない理由を plan.md に
  記録しなければならない（MUST）。
- 複雑さを導入する場合は、plan.md の Complexity Tracking に、より単純な代替案を
  採用しなかった理由を記載しなければならない（MUST）。

**Rationale**: 個人開発の画像ビューアでは、機能の多さより保守しやすさと速さが重要である。

## 技術的制約

- 形態: デスクトップアプリケーション。主対象プラットフォームは macOS とする。他 OS への
  対応は spec で明示された場合のみ行う。
- UI フレームワークおよび言語は本憲章では固定しない。最初の機能の plan で選定し、
  原則 I〜V（特にオフライン動作、性能基準、アクセシビリティ API 対応）を満たせることを
  根拠として plan.md に記録しなければならない（MUST）。
- 対応画像形式は spec で定義する。非対応形式はクラッシュせず、ユーザーに分かる形で
  通知しなければならない（MUST）。
- 設定や閲覧履歴などのアプリデータは、OS 標準のアプリケーションデータ領域に
  ローカル保存する（原則 I）。

## 開発ワークフローと品質ゲート

- 機能開発は Spec Kit の流れ（/speckit-specify → /speckit-plan → /speckit-tasks →
  /speckit-implement）に従う。
- plan.md の Constitution Check で原則 I〜V への適合を確認し、違反がある場合は
  Complexity Tracking に正当化を記載しなければならない（MUST）。
- マージ前のゲート:
  - 自動テストがすべて通過していること（原則 IV）
  - 性能に影響する変更では計測結果が記載されていること（原則 II）
  - 新しい操作にキーボード手段があること（原則 III）
  - 外部通信が追加されていないこと（原則 I）

## 仕様の管理

- 現在の仕様の正本は `specs/product/` の領域別のファイル（Living spec）とする。
  横断の契約は `specs/product/contracts/` に置く。
- 新しい要件・変更は、`/speckit-specify` で新しい feature ディレクトリ（`specs/NNN-xxx/`）を作って扱う。
  完了した feature ディレクトリの spec.md へ要件を追加してはならない（MUST NOT）。
- feature の spec.md には変更点だけを書き、既存の要件は `specs/product/` の ID で参照する。
  plan・tasks・analyze・converge は、feature の spec.md と、参照している `specs/product/` の領域をあわせて入力とする。
- feature の実装と検証が終わったら、変更点を `specs/product/` の該当する領域へ反映し、その feature ディレクトリは
  凍結する（以後は実装の経緯の記録として扱い、更新しない）（MUST）。
- FR・SC などの ID は全領域で一意とし、振り直しも再利用もしない。ID の付け方は `specs/product/README.md` に従う。

## Governance

- 本憲章は、プロジェクトの他のすべての慣行・ガイドラインに優先する。
- 改定は `.specify/memory/constitution.md` の更新として行い、変更理由と影響範囲を
  Sync Impact Report に記録する。影響を受ける既存の spec / plan があれば、改定と
  同時に追従方針を明記しなければならない（MUST）。
- バージョニングはセマンティックバージョニングに従う:
  - MAJOR: 原則の削除、または後方互換性のない再定義
  - MINOR: 原則・セクションの追加、またはガイダンスの実質的な拡張
  - PATCH: 文言の明確化、誤字修正など意味を変えない修正
- 各 plan の Constitution Check およびマージ前レビューで本憲章への適合を確認する。
  憲章と実態が乖離した場合は、実装を直すか憲章を改定するかのいずれかを選び、
  放置してはならない（MUST NOT）。
